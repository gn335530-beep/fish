# 行情魚種改以官方代碼字典解析

**Status:** ready-for-agent

**Source:** 2026-10-28 對話：使用者要求「輸入魚種 → 查詢魚種代碼 → 查詢價格 → 回傳資料」，並決定刪除既有 28 種 `species.js`、`species_id` 與料理資料。

## Problem Statement

目前行情查詢只認得系統內的 28 種魚。使用者輸入「土魠魚」「吳郭魚」「鮭魚」等官方行情其實有代碼的魚種時，系統在第一步就用 28 種白名單擋掉，直接回「暫無行情」，不會去查官方代碼，也不會查價格。

同時，這 28 種同時綁定上架辨識、商品 `species_id`、學名與料理資料。只要魚種不在清單內，商品就沒有代碼、沒有料理資料，行情也查不到。維護者必須手動維護「系統魚種 → 官方代碼」對照，無法涵蓋官方每天出現的 200 多個新鮮代碼。

使用者要的是單純且可預期的流程：

```
輸入魚種名稱
→ 查官方代碼
→ 用代碼查價格
→ 回傳代碼、名稱、均價、交易日、縣市／全國、來源
```

## Solution

建立一份執行時同步的官方新鮮代碼字典，讓行情查詢以官方代碼為唯一鍵：

- 使用者輸入名稱或代碼，系統先查字典。
- 只有一個候選時，直接用該代碼查行情。
- 多個候選時，回傳候選清單讓使用者選擇，不自動猜測。
- 完全查不到時，明確回「查無此魚種代碼」。
- 查代碼與查價格都由後端完成，前端只負責輸入、候選選擇與顯示。

同時移除舊的 28 種魚種模型：

- 不再有 `species.js`、`/api/species`、`species_id`、`species_latin`。
- 商品只保留使用者輸入的魚種名稱與可選的官方代碼。
- 既有商品的魚種相關欄位在啟動時清空，`fish_species` 保留。
- 料理資料、學名、肉質、刺與料理方式篩選一併移除。

## User Stories

1. 作為買家，我想輸入「土魠魚」就查到官方行情，而不是被 28 種白名單擋掉，以便查詢更多魚種。
2. 作為買家，我想輸入「吳郭魚」就查到官方行情，以便不必知道官方代碼。
3. 作為買家，我想輸入「鮭魚」就查到官方行情，以便查詢非本地常見魚種。
4. 作為買家，我想直接輸入官方代碼查行情，以便在知道代碼時快速查詢。
5. 作為買家，我想在回覆中看到魚種代碼與官方名稱，以便確認系統查的是正確魚種。
6. 作為買家，我想在回覆中看到平均價、交易日期、縣市或全國平均與來源，以便判斷價格是否可信。
7. 作為買家，我想在名稱對到多個官方代碼時看到候選清單，以便選擇正確的魚種。
8. 作為買家，我想在候選回覆後直接回覆其中一個名稱，以便完成查詢，不必重新描述完整句子。
9. 作為買家，我想在查無魚種代碼時看到明確訊息，以便知道不是行情壞掉。
10. 作為買家，我想在魚種有代碼但當日沒有交易時看到「暫無行情」，以便區分查無魚種與查無交易。
11. 作為買家，我想在上游失敗但本機有舊資料時看到上次成功的行情與交易日期，以便不會因暫時斷線而完全查不到。
12. 作為買家，我想用常見別名查詢，例如「嘉鱲」「赤鯮」「海鱸」「竹筴魚」，以便不用記官方名稱。
13. 作為買家，我想讓「土魠魚」對到官方「土魠」，以便常見說法也能查。
14. 作為買家，我不想系統自動把「石斑」猜成某一種石斑，以便避免查到錯誤魚種。
15. 作為買家，我想在「石斑」這類名稱看到石斑魚、龍膽石斑、其他石斑魚等候選，以便自行選擇。
16. 作為釣客，我想上架時仍可輸入自由魚種名稱，以便官方字典沒有的魚也能上架。
17. 作為釣客，我想上架草稿保存官方代碼，以便發布後仍能對應正確魚種。
18. 作為釣客，我想在魚種有多個代碼時仍可先完成上架，以便不被行情查詢阻擋。
19. 作為釣客，我想在魚種查無代碼時仍可發布商品，以便不影響主要交易流程。
20. 作為釣客，我想在上架行情卡看到正確魚種的行情，以便定價。
21. 作為釣客，我想在行情卡顯示候選魚種時先選魚種，以便參考金額不會套錯魚。
22. 作為買家，我想商品詳情不再顯示學名與料理資料，以便畫面只保留實際商品資訊。
23. 作為買家，我想商品卡不再依賴 `species_id` 顯示「未知魚種」，以便沒有代碼的商品也能正常呈現。
24. 作為買家，我想商品列表仍可用魚種名稱與地區篩選，以便找到想買的魚。
25. 作為買家，我想導購不再用料理方式與肉質篩選，以便行為與現有資料一致。
26. 作為維護者，我想在啟動後第一次查詢時自動同步官方代碼字典，以便不需要每天手動跑 job。
27. 作為維護者，我想字典同步快取 24 小時，以便不會每次查詢都抓全量官方資料。
28. 作為維護者，我想字典同步支援分頁，以便取得超過單次上限的官方資料。
29. 作為維護者，我想字典排除凍結與加工代碼，以便只保留新鮮行情。
30. 作為維護者，我想字典保留同一代碼的不同官方名稱，以便名稱變動時仍可查到。
31. 作為維護者，我想字典同步失敗時沿用舊字典，以便上游暫時失敗不會讓所有查詢失效。
32. 作為維護者，我想完全沒有字典時回傳明確錯誤，以便區分「尚未同步」與「查無魚種」。
33. 作為維護者，我想行情價格以 `species_code` 為唯一鍵，以便查詢邏輯不再依賴 `species_id`。
34. 作為維護者，我想移除 `/api/species` 與 `species_market_codes`，以便魚種來源只剩官方代碼字典。
35. 作為維護者，我想舊商品的 `species_id` 與 `species_latin` 在啟動時清除，以便資料模型與新程式一致。
36. 作為維護者，我想舊商品的 `fish_species` 保留，以便商品名稱與歷史資料不變。
37. 作為維護者，我想 CLI 可以用代碼查行情，以便手動除錯。
38. 作為維護者，我想 CLI 也可以用名稱查代碼，以便不用先查文件。
39. 作為維護者，我想 API 文件與 ADR 更新為代碼字典模型，以便後來的人不會再找 `species_id`。
40. 作為維護者，我想所有程式碼檔案維持 200 行以下，以便符合專案規範。

## Implementation Decisions

### 官方代碼字典

- 新增「官方新鮮代碼字典」與「字典同步狀態」兩份資料。
- 字典欄位包含：代碼、官方名稱、別名、分類、養殖旗標、最後出現日期。
- 同步範圍為官方最近 30 天資料，使用 `$top=10000` 與 `$skip` 分頁。
- 排除 `3xxx` 凍結與 `6xxx` 加工代碼；保留 `1xxx`、`2xxx`、`4xxx`、`5xxx`。
- 同一代碼跨日期出現多個名稱時，全部保留為別名。
- 同步成功後快取 24 小時；啟動時可背景觸發，不阻塞伺服器啟動。
- 同步失敗時沿用既有字典；完全沒有字典才回傳字典不可用。
- 同一時間只允許一個同步進行，避免重複抓取。

### 名稱解析

- 支援精確官方名稱、精確別名與純數字代碼。
- 不做「魚／海／養」等後綴去除。
- 不做模糊搜尋或錯字修正。
- 建立一份小型常見別名表，補官方名稱與使用者說法的差異，例如土魠魚、嘉鱲、赤鯮、海鱸、竹筴魚。
- 同一個名稱對到多個代碼時，一律回傳候選清單，不自動選擇。
- 候選需包含代碼、官方名稱、是否養殖，並以穩定順序排列。

### 養殖旗標

- 官方名稱含「養」時標記為養殖。
- 少數沒有「養」字但既有系統視為養殖的代碼，使用代碼旗標表補齊。
- 不再依賴舊的 28 種養殖清單。

### 行情 API

- 查代碼端點接受名稱、別名或數字代碼；省略查詢時回傳完整字典。
- 查價端點只接受 `code`，不再接受 `species_id`。
- 整合查詢端點接受名稱與地區，內部完成查代碼與查價格。
- 單一候選直接回行情；多候選回 `AMBIGUOUS_SPECIES` 與候選；查無回 `SPECIES_NOT_FOUND`。
- 行情回應包含 `species_code`、`official_name`、均價、交易日期、縣市或全國、來源與養殖旗標。
- 保留既有 `NO_TRADE_DATA`、`UPSTREAM_UNAVAILABLE` 與台斤換算規則。
- 每次價格查詢仍重抓上游；字典同步與價格查詢是兩個不同的快取層。

### 商品模型

- 商品移除 `species_id` 與 `species_latin`。
- 商品新增可選的 `species_code`。
- 商品仍保留 `fish_species`，作為使用者輸入的魚種名稱。
- 建立商品時不因查無代碼或多候選而失敗。
- 商品查詢的魚種篩選改用 `fish_species`。
- 商品卡不再以 `species_id` 判斷未知魚種。

### 前端

- 移除舊的魚種 API 用戶端、魚種查詢模組與 `/api/species` 載入。
- 新增前端魚種字典模組：載入完整字典、同步比對名稱、呼叫查代碼端點。
- 將地區正規化與地區解析從舊魚種模組搬到獨立地區模組。
- 上架草稿、修改草稿與發布流程改存 `species_code`。
- 上架行情卡優先使用草稿代碼；沒有代碼時用魚種名稱查整合行情。
- 對話問行情改成：名稱 → 查代碼 → 單一候選查價／多候選回問。
- 多候選的待選狀態存在對話 context，下一句可比對候選。
- 導購移除料理方式與肉質篩選，只保留魚種名稱、地區與商品欄位。
- 商品諮詢移除料理資料回覆，只回商品資訊。
- 商品詳情移除學名與料理資料欄位。

### 遷移

- 啟動時清除既有商品的 `species_id` 與 `species_latin`。
- 既有商品的 `species_code` 設為 `null`，不自動回填。
- 既有商品的 `fish_species` 保留。
- 行情資料與抓取狀態移除 `species_id` 欄位，改用 `species_code`。
- 移除舊的魚種對照資料。

### 移除範圍

- 刪除舊魚種清單模組、魚種路由與魚種 API 用戶端。
- 刪除舊魚種查詢、`speciesById`、`speciesList`、`findSpecies` 的使用。
- 刪除料理資料與相關顯示、篩選。
- 移除 `/api/species`、`/api/market/species-codes` 與 `species_market_codes`。

### 文件

- 新增 ADR，記錄「以官方代碼字典取代固定魚種清單」。
- 更新行情、商品、上架、對話、導購與 API 文件。
- 更新 glossary，移除 `species_id` 與料理資料相關舊詞，加入官方代碼字典、候選魚種等詞彙。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、對話回覆、草稿內容、畫面輸出與遷移後的資料。測試不驗私有函式名稱、不驗內部呼叫次數，也不為了測試把模組拆得更細。

沿用 4 個既有斷層：

1. **後端 HTTP（最高層）**
   - 用既有測試伺服器與假上游，涵蓋字典同步、查代碼、整合查詢、代碼查價與商品建立。
   - 既有前例：行情 API 測試、行情快取測試、商品建立測試。

2. **前端對話與上架流程**
   - 用既有假 API fixture 跑助手流程，涵蓋名稱查代碼、候選追問、上架草稿與行情卡。
   - 既有前例：上架行情卡測試、行情問答測試、上架草稿測試。

3. **前端商品顯示**
   - 用既有 HTML 字串與 VM 測試，涵蓋商品卡、商品詳情與無代碼商品。
   - 既有前例：商品卡測試、商品標題測試、格式測試。

4. **既有資料遷移**
   - 直接呼叫商品資料正規化，驗證舊欄位被清除、名稱保留。
   - 既有前例：商品資料遷移測試。

需新增或擴充的案例：

- 字典同步會分頁取得全部資料，並排除凍結與加工代碼。
- 同一代碼出現多個名稱時，所有名稱都能查到該代碼。
- 精確名稱、別名、數字代碼都能查到候選。
- 多個代碼同名時回傳候選，且不自動選第一個。
- 查無名稱時回 `SPECIES_NOT_FOUND`。
- 字典同步失敗但已有舊字典時，查詢仍可用。
- 完全沒有字典時回 `CATALOG_UNAVAILABLE`。
- 代碼查價回傳代碼、官方名稱、均價、交易日期與來源。
- 上游失敗但有舊行情時回舊資料。
- 商品建立不再寫 `species_id` 與 `species_latin`，可接受可選 `species_code`。
- 舊商品在遷移後保留 `fish_species`，但沒有 `species_id`、`species_latin`，`species_code` 為 `null`。
- 對話輸入土魠魚時完成查代碼與查價。
- 對話輸入多候選名稱時回問候選，下一句可完成查詢。
- 上架草稿保存 `species_code`，查無代碼仍可繼續。
- 商品卡與詳情頁不再顯示學名、料理資料或依 `species_id` 顯示未知魚種。
- 導購不再使用料理方式與肉質篩選。

完整測試以既有 `npm test` 執行。

## Out of Scope

- 不做模糊搜尋、注音搜尋或錯字自動修正。
- 不去除「魚／海／養」等後綴；需要時以別名表補。
- 不保留料理資料、學名、肉質、刺或料理方式篩選。
- 不重新加入固定魚種白名單。
- 不恢復商品行情快照或商品卡行情顯示。
- 不改變行情只引用官方開放資料的原則。
- 不改台斤換算、交易房、訂單、協議或評價流程。
- 不建立新的資料庫或遷移框架；沿用現有 JSON 資料與啟動正規化。
- 不新增前端框架、建置工具或新的執行期依賴。
- 不保證每個官方代碼每天都有交易；查無交易仍回 `NO_TRADE_DATA`。

## Further Notes

- 這是 breaking change：`species_id`、`species_latin`、`/api/species`、`/api/market/species-codes` 與 `species_market_codes` 都會移除。
- 與 ADR 0003（行情只引用官方資料）相容；與 ADR 0004／0006（按需抓取、每次查詢重抓）相容；ADR 0004 已被 0006 取代。
- 與 ADR 0007（移除商品行情快照）相容，本 spec 不恢復商品快照。
- 第一次查詢可能需要同步字典，預期多 1–3 秒；之後 24 小時內使用快取。啟動時可背景同步以降低首次延遲。
- 官方名稱可能因日期與市場而變動；字典保留同一代碼的多個名稱，查詢時以代碼為準。
- 多候選是刻意的設計：寧可多問一次，也不要查錯魚種。
- 風險：官方 API 分頁行為若與預期不同，需以實際回傳筆數判斷停止條件；字典同步失敗時必須保留舊資料。
- 每個程式碼檔案以 200 行為硬上限；字典同步、搜尋與價格查詢若接近上限，依職責拆檔。
- 領域用語以 `GLOSSARY.md` 為準：行情、魚種、代碼、商品、上架、助手、對話、交易房。文案不出現 Avoid 詞。
- 完成條件：`npm test` 全綠；所有程式碼檔案 ≤200 行；4 個測試斷層的新案例都有涵蓋；文件與 ADR 更新完成。
