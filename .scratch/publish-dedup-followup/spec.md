# 上架去重後續修正：舊草稿識別碼、測試鎖定與文件對齊

**Status:** resolved

**Source:** 2026-11-17 對 `97b4fd5`（publish dedup tickets 01–03）的雙軸 code review。Standards 軸 1 項硬性違規、4 項判斷性 smell；Spec 軸 6 項發現。

## Problem Statement

上架防重複已讓新草稿在連點與重試時只建立一筆商品，但改版前留下的上架草稿沒有發布識別碼。原批次規格寫明「不為舊草稿回填」，實際上草稿只要經過一次文字修改就會取得新的識別碼。釣客從畫面看不出差異；維護者卻會得到兩種互相矛盾的說法，不確定舊草稿到底有沒有後端去重保護。若有人照著文件移除這個行為，舊草稿在上架成功、後續訊息或 context 寫入失敗後重試時，就可能再次產生重複商品。

第二個問題是測試沒有把保證鎖死。發布中的三個動作是否全部停用，發布流程測試只斷言畫面出現 disabled；修改草稿後識別碼不變、新草稿換新識別碼只在草稿模組層驗證；「上架紀錄只多一筆」是用單一商品 id 過濾，而不是比較總數。這些斷言在重構或調整測試時很容易失效，讓回歸保護看起來存在、實際卻漏掉。

第三，少量可維護性問題增加修改成本：後端識別碼格式常數的名稱像欄位值；前端發布測試重複貼上商品 fixture 與延遲 gate。最後，發布失敗的提示規則在文件與程式之間有字面落差：文件寫「面板提示與 toast」，程式在釣客已切換房間時只顯示 toast。實際行為是對的，但沒有被文件說清楚。

## Solution

- 正式採用「舊草稿在第一次以文字修改欄位時補上發布識別碼」的行為：不改程式，改文件與測試。理由是它讓舊草稿也取得後端去重保護，識別碼不外露，且沒有使用者可見的代價。
- 把原批次規格中「不為舊草稿回填」的決定標記為已被本 spec 取代，並在 living spec 的流程與 UI 章節寫清楚。
- 補強兩個既有最高測試斷層：前端發布流程與後端 HTTP。
- 將重複的發布測試 fixture 與延遲 gate 收進共用 fixture；後端格式常數改名為 pattern。
- 把失敗提示規則寫成：toast 一律顯示；面板提示只在原本送出的助手房仍是目前房間時顯示。
- 不改 API 契約、不改識別碼格式、不改發布流程的模組歸屬、不新增 UI 文案或 Playwright 案例。

## User Stories

1. 作為使用改版前草稿的釣客，我想在第一次以文字修改草稿欄位時自動取得發布識別碼，以便後續重試也受後端去重保護。
2. 作為釣客，我不想看到發布識別碼，以便畫面只顯示漁獲與價格。
3. 作為釣客，我想在補值後繼續修改魚種、尾數、處理方式、照片或售價，以便識別碼不會因修改而換新。
4. 作為釣客，我想在重新整理後重試同一份草稿時仍帶同一個識別碼，以便網路不穩不會造成重複上架。
5. 作為釣客，我想在建立商品成功但後續訊息失敗後重試，仍拿到同一筆商品，以便部分失敗也能安全復原。
6. 作為釣客，我想在發布成功後開新草稿時取得新識別碼，以便刻意再上架一批相同的魚。
7. 作為釣客，我想在按下確認上架後立刻看到「上架中…」，以便知道點擊已被接收。
8. 作為釣客，我想在發布期間看到三個動作都停用，以便不會再按第二次。
9. 作為釣客，我想連點確認上架只建立一筆商品，以便不必擔心手誤。
10. 作為使用慢網路的釣客，我想在等待時安心等系統完成，以便不會因為沒回饋而重複操作。
11. 作為釣客，我想在原房間看到失敗的面板提示與 toast，以便知道這次沒有成功。
12. 作為釣客，我想在切換房間後仍看到失敗 toast，以便不會漏掉錯誤。
13. 作為釣客，我不想在目前房間看到另一間房的失敗面板提示，以便不被無關錯誤干擾。
14. 作為釣客，我想讓發布成功的結果只寫回原本送出的助手房，以便不污染另一間對話。
15. 作為釣客，我想在切換房間後讓目前房間的訊息不被替換，以便保有正在看的內容。
16. 作為使用鍵盤或螢幕閱讀器的釣客，我想在發布期間取得 `aria-busy` 與停用狀態，以便知道系統正在處理。
17. 作為買家，我想在公開商品列表只看到一筆真正的上架批次，以便不會把重複項目誤認為還有更多庫存。
18. 作為買家，我想在助手房的商品結果看到去重後的商品，以便推薦內容值得信任。
19. 作為釣客，我想在上架紀錄只看到一筆這次發布，以便管理商品時不必手動刪除重複項。
20. 作為釣客，我想在遇到既有重複商品時仍能從上架紀錄下架或刪除，以便清理舊資料。
21. 作為維護者，我想在發布流程斷層看到「三個動作全部停用」的明確斷言，以便部分鎖定不會漏過。
22. 作為維護者，我想在發布流程斷層驗證修改草稿後識別碼不變，以便保證不只在草稿模組層成立。
23. 作為維護者，我想在發布流程斷層驗證新草稿會換新識別碼，以便「刻意再上架」不會被誤擋。
24. 作為維護者，我想在後端斷層比較上架紀錄總數只增加一筆，以便重送不會偷偷多列一筆。
25. 作為維護者，我想讓舊草稿的 lazy backfill 有流程級測試，以便文件與行為永遠一致。
26. 作為維護者，我想讓格式常數的名稱表達它是 pattern，以便不會被誤認為欄位值。
27. 作為維護者，我想讓發布測試共用 gate 與商品 fixture，以便一處修改就能更新所有測試。
28. 作為維護者，我想讓 living spec 與原批次 spec 的註記反映最新決定，以便讀文件的人不會得到舊答案。
29. 作為維護者，我想讓所有修改檔案維持在 200 行以內並讓 `npm test` 通過，以便符合專案規範。
30. 作為 reviewer，我想讓 e2e selector 與 docs summary 的更新被記錄為刻意修正，而不是默默越界。

## Implementation Decisions

### 舊草稿的發布識別碼

- 維持現行 lazy backfill：沒有識別碼的上架草稿在第一次以文字修改魚種、尾數、處理方式或售價時，由草稿合併流程補上一組新的發布識別碼，並隨助手房的 context 保存。
- 透過「修改草稿」換照片走既有的照片更新流程，不合併草稿欄位，因此不會為尚未補值的舊草稿補識別碼；上架流程中直接上傳照片仍會合併草稿並補值。已有識別碼的草稿修改照片時仍保留同一個。
- 尚未修改的舊草稿維持沒有識別碼；不執行批次遷移、不在讀取時補值。
- 補值後同一份草稿的識別碼在後續修改、重新整理、上架部分失敗後重試時都不變。
- 只有建立全新草稿、發布成功或草稿重設後才換新識別碼。
- 此決定取代原批次規格「不為舊草稿回填」與「舊草稿不保證跨重新整理重試」兩點；以原批次 spec 底部的 Comments 註記，不重寫歷史本文。
- 不改前端程式；識別碼仍不顯示、不由商品 API 回傳。

### 文件

- living spec 的「確認上架」流程補上：改版前建立且沒有識別碼的草稿，在第一次以文字修改欄位時取得識別碼；未修改前仍只有前端防連點；只改照片不補值。
- UI 章節的發布失敗段落改成：toast 一律顯示；面板錯誤提示只在原本送出的助手房仍是目前房間時出現。
- Roadmap 的防重複驗收條件補上舊草稿 lazy backfill。
- 原批次 spec 的 Comments 加一則註記，指出舊草稿與失敗提示兩點由本 spec 取代。
- 本次 review 已更新的 `docs/api/README.md` 與 `docs/spec/README.md` 屬 AGENTS.md 要求的文件同步，保留不動。

### 後端常數

- 把識別碼格式常數改名為表達「pattern」的名稱。
- 行為、驗證順序、HTTP 狀態與錯誤碼完全不變。

### 測試 fixture

- 共用發布 fixture 增加可重用的「延遲 gate」helper，回傳 promise 與 release 函式；測試不再各自複製 gate 樣板。
- 共用發布 fixture 提供標準商品資料；前端測試不再硬編商品標題字面值。後端測試沿用既有的上架紀錄 helper，不新增 fixture 層。
- 不新增測試框架、不新增 API stub、不為了測試拆模組。

### 錯誤提示

- 行為不變：toast 一律；面板提示只在原房間。
- 以既有房間安全測試為準，不新增案例；只更新文件措辭。

### 刻意保留

- 識別碼格式維持時間戳＋序號＋亂數。序號在頁面重新載入後會歸零，只靠序號可能與已保存在對話 context 的識別碼碰撞，讓後端誤回舊商品。
- 發布流程留在對話流程模組；不搬到上架對話模組。發布是跨 API 的流程編排，不是對話語意。
- `assistant-offline` e2e 的 selector 收窄保留：它讓測試只點房間列，屬於測試強健性修正，不改變產品行為。
- 本次不 bump 前端快取版本：沒有變更任何前端資產。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、發布流程送出的請求、發布後的訊息與 context、畫面渲染出的文字與屬性。測試不驗私有函式名稱、不驗內部呼叫堆疊、不為了測試把模組拆得更細。

沿用兩個既有最高斷層，不新增斷層：

1. **後端 HTTP**
   - 使用既有測試伺服器、登入 Token 與商品建立 helper；既有前例是 `product-idempotency.test.js`。
   - 保留既有的重送、不同識別碼、不同釣客、沒有識別碼、非法識別碼與硬刪後重建案例。
   - 新增：同一釣客帶相同識別碼重送前後，比較上架紀錄總數只增加一筆；回應仍不含識別碼。
   - 不新增端點或錯誤碼測試。

2. **前端發布流程**
   - 使用既有假 `HaisenAPI`、訊息 factory 與共用 fixture；既有前例是 `publish-draft.test.js` 與 `publish-room-safety.test.js`。
   - 連點測試改為明確斷言渲染結果同時包含「上架中…」、三個 `disabled` 與 `aria-busy`，不再只斷言出現一次 disabled。
   - 既有「建立成功、訊息寫入失敗後重試」測試延長為：失敗後先修改草稿欄位，再重試；兩次建立商品的識別碼必須相同。
   - 新增：成功發布後建立新草稿並發布，送出的識別碼與前一次不同。
   - 新增：未修改的舊草稿直接發布時，請求不帶識別碼；先修改再發布時，請求帶新識別碼，且部分失敗後重試沿用同一個。
   - 既有切房成功、切房失敗、面板提示與 toast 的案例維持，不新增 Playwright 案例。
   - 草稿卡渲染與草稿模組的既有測試保留，但不加新斷言；新的保證由發布流程斷層驗證。

不新增 Playwright 連點或慢網路案例；快取版本 e2e 維持現有鎖定版本，因為本次沒有前端資產變更。

## Out of Scope

- 不自動刪除或合併已經存在的重複商品；仍由釣客從上架紀錄處理。
- 不以內容相似度去重；只認明確的發布識別碼。
- 不改 API 契約、錯誤碼、識別碼格式或資料模型。
- 不為未修改的舊草稿批次補值，也不在讀取時補值。
- 不新增 Playwright 連點、慢網路或切房案例。
- 不改前端資產，因此不快取版本 bump。
- 不搬移發布流程、不拆對話流程模組。
- 不新增 ADR 或 glossary 名詞；這是既有行為的文件對齊與測試補強。
- 不改商品照片、價格、庫存、列表排序或交易房 UI。
- 不重寫原批次 spec 的歷史本文，只加 Comments 註記。

## Further Notes

- Lazy backfill 沒有使用者可見代價：識別碼存在草稿物件與商品資料中，草稿卡不顯示，商品 API 也不回傳。它只讓舊草稿在第一次以文字修改後享有與新草稿相同的重試保護。
- 尚未修改或只透過「修改草稿」換照片的舊草稿仍只有前端防連點；若上架成功但後續步驟失敗，重試可能產生第二筆。這是原 spec 已接受的限制，本次不擴大處理。
- 識別碼格式刻意保留三種來源：時間戳處理跨重新載入、序號處理同一毫秒內的同頁建立、亂數降低碰撞。三者缺一都可能讓後端把新草稿誤認成舊商品。
- 本次 review 的 Feature Envy 建議（把發布收尾搬到上架對話模組）與 Speculative Generality 建議（簡化識別碼格式）都刻意不採納；理由如上述，且搬移會擴大變更面。
- `assistant-offline` 的 selector 收窄與 docs summary 更新屬刻意的測試強健性與文件同步修正，不是偷偷擴大功能範圍。
- 所有修改與新增檔案必須維持在 200 行以內；完成後 `npm test` 應全綠。
