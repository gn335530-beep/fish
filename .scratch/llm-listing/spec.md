# 模型驅動的對話式上架：錯字修正、直接覆寫與基本模式

**Status:** ready-for-agent

**Source:** 2026-11-21 使用者需求「我需要 LLM 模型在上架時協助我進行上架，例如修正錯字等等」；經 grilling 逐項確認：模型直接覆寫草稿、全程參與上架對話、官方代碼字典是魚種唯一權威、修正需在對話中告知、AI 故障時切換基本模式、沿用既有測試斷層。

## Problem Statement

釣客在助手房上架漁獲時，目前仍由規則引擎主導：釣客要照固定順序回答魚種、尾數、處理方式、照片與售價；魚種或處理方式打錯字時，系統不會修正；想改草稿要先按「修改草稿」，再一項一項回答。即使 `LLM_ENABLED=true`，模型也只能提供 intent 與 slots，平台意圖的文字與草稿更新仍由規則決定，模型不能自然對話、不能修正錯字，也不能直接更新草稿。

釣客因此需要反覆打字、自己發現錯字、自己把口語句子拆成欄位；遇到「土魠」「鬼投刀」這類名稱時，也不知道系統會查到哪個官方魚種。另一方面，平台不能讓模型亂改價格、尾數或魚種，也不能讓模型代替釣客發布商品。

這個功能要讓 LLM 在整個上架過程協助釣客，包括修正明顯錯字、聽懂口語、直接更新草稿；同時保留可見的修正告知、可改回原字串的逃生門，以及模型故障時仍能完成上架的基本模式。

## Solution

- `LLM_ENABLED=true` 且模型可用時，助手房以模型驅動上架：模型聽懂每一則訊息、抽出欄位、直接更新草稿、決定下一個要問的欄位，並在適當時機顯示行情卡與草稿卡。
- 模型只回傳草稿變更、修正紀錄、告知文字與下一個動作；實際驗證、草稿寫入、卡片渲染與商品發布仍由程式執行。
- 魚種以官方代碼字典為唯一權威：合法別名不改；只有原字串查無、且修正後剛好對到唯一官方名稱時，才修正並在對話中告知。
- 多個候選魚種時問「A 還是 B」；完全查不到時問一次是否仍要上架；釣客可明確說「保留我打的字」，該字串在同一間助手房不再自動修正。
- 處理方式保留釣客原句，只修明顯錯字；超過 20 字或只有數字／單位時回問，兩次無效後可在對話中提議縮短版，釣客同意才套用。
- 釣客可一次修改多個欄位，直接打字即可，不需要「修改草稿」按鈕；正常模式下草稿卡只有「確認上架」與「取消上架」。
- 模型無法使用時切換基本模式：顯示一次提示、改走規則引擎、草稿卡恢復「修改草稿」按鈕；基本模式維持到釣客開新助手房。
- `LLM_ENABLED=false` 時維持今天的規則模式，不顯示 AI 故障提示。交易房永遠不呼叫 LLM。

## User Stories

3. 作為釣客，我想讓助手修正魚種的明顯錯字，以便商品使用正確名稱。
4. 作為釣客，我想在助手修正錯字時被告知「什麼改成什麼」，以便我能發現改錯。
5. 作為釣客，我想用打字說「不是，保留我打的字」，以便助手不會再把我的當地叫法改掉。

48. 作為維護者，我想尾數與售價必須出現在釣客訊息，以便模型不能編造數字。

51. 作為維護者，我想交易房永遠不呼叫 LLM，以便私人交易對話不外送。

53. 作為維護者，我想沿用既有 HTTP、對話流程與草稿卡測試斷層，以便不新增測試框架。

## Implementation Decisions

### 模式與開關

- 不新增功能旗標；`LLM_ENABLED=true` 且模型可用時，助手房的上架流程由模型驅動。
- `LLM_ENABLED=false` 時維持現行規則上架、草稿卡顯示「修改草稿」按鈕，不顯示 AI 故障提示。
- 交易房永遠不呼叫 LLM，維持 ADR-0011 對交易房的限制。
- 模型逾時、429、無金鑰、上游錯誤或格式錯誤時切換基本模式；基本模式寫進該助手房的 context，重新整理仍維持，開新助手房才重新嘗試模型。
- 基本模式提示只顯示一次：「AI 暫時無法協助，已切換基本模式；你仍可完成上架。」
- `LLM_DISABLED`（旗標關閉）不算故障，不顯示提示。
- 模型回覆的欄位驗證失敗（魚種修正不合法、數字不在訊息中、動作時機不對）只丟棄該輪模型回覆並改用規則，不切換基本模式；避免一次壞輸出就永久降級。
- 不自動排隊、不自動重試；429 時直接走基本模式。

### 模型驅動的上架對話

- 模型每一輪會收到目前草稿、缺少欄位、魚種精確查詢結果、使用者確認字串、修正歷史、待同意的處理方式縮短版、處理方式回問次數、是否有照片，以及最近對話。
- 模型回傳：回覆文字、修正告知、草稿變更、修正紀錄、新增的使用者確認字串、處理方式縮短提議、處理方式回問訊號、下一個動作。
- 下一個動作只有「問問題」、「顯示行情卡」、「顯示草稿卡」、「不動作」四種；顯示時機由程式再驗一次。
- 模型可以調整提問順序，但價格必須最後問；非價格欄位（魚種、尾數、處理方式）可以合併問；照片只用上傳事件填入。
- 非價格欄位完成前不得問售價、不得顯示行情卡；所有欄位完成後才顯示草稿卡。
- 模型只改「這一則訊息明確提到」的欄位，不對整份草稿做背景重審。
- 模型可以簡短回答與上架無關的問題，但不得因此修改草稿，也不得編造行情、庫存或售價。
- 顯示草稿卡時，回覆文字要包含「想修改直接告訴我」；草稿卡本身不加這行文字。
- 取消上架與確認上架仍由按鈕與規則處理；模型沒有發布、下架或刪除權限。

### 魚種與官方代碼字典

- 魚種以官方代碼字典為唯一權威；不引入外部學名或生物分類名稱。
- 原字串精確查詢有候選（含合法別名）時，保留釣客原文，不修正。
- 原字串只有一個候選時，草稿使用該候選的官方代碼；商品上的魚種文字仍是釣客原文。
- 原字串對到多個候選時，助手問「是哪一種？A、B」，不替釣客選；釣客可明確說「都不是，保留我打的字」，此時保留原文、代碼留空、行情暫無。
- 原字串完全查無時，助手問一次「查不到這個魚種，仍要上架嗎？」；釣客確認後保留原文、加入使用者確認字串，之後不再追問。
- 錯字修正只允許在下列條件全部成立時發生：原字串精確查詢為 0 個候選；模型提出修正後的名稱；該名稱精確查詢剛好 1 個候選；目前草稿值等於原字串；原字串不在使用者確認字串中。
- 模型在提出魚種修正前必須使用唯讀的官方字典查詢工具確認修正後名稱；後端會再驗一次，不信任模型單方面說法。
- 魚種修正成功時，助手在對話中告知「我把魚種『鬼投刀』修正為『鬼頭刀』」，並更新草稿與官方代碼。
- 釣客說「不是，我要保留原字串」時，助手把原字串寫回草稿，並加入使用者確認字串；同一間助手房不再自動修正該字串。
- 釣客改變魚種時，舊的官方代碼與行情快取要失效，重新查詢。

### 處理方式

- 處理方式保留釣客原句；模型只修明顯錯字，不改寫語意。
- 處理方式最多 20 字，且不能只有數字或單位；違反時助手回問並顯示目前字數。
- 兩次回問仍無法符合時，助手可在對話中提議一個 20 字內的版本；提議要存進待同意的處理方式縮短版，釣客明確說「好」或「套用」才寫入草稿。此提議由後端把關：只有在回問計數已達兩次時才接受，未達兩次時丟棄提議並降級成回問。模型回問處理方式時要送出回問訊號，後端據以遞增回問計數；處理方式寫入有效值後計數歸零。
- 處理方式的錯字修正要通過後端編輯距離檢查（上限 2）；超過上限視為改寫，丟棄該修正。
- 任何處理方式修正或經同意的縮短，都要在對話中告知；長度縮短不算錯字修正，不寫入修正紀錄的 `corrections`。
- 處理方式的錯字沒有官方字典可驗證，這是本功能的殘餘風險；靠對話告知與釣客改回來補救。

### 草稿修改與數字

- 釣客可直接用文字修改草稿，不需要「修改草稿」按鈕；一次可修改多個明確提到的欄位。
- 正常模型模式下，草稿卡只有「確認上架」與「取消上架」；基本模式才恢復「修改草稿」。
- 尾數、整批售價、每台斤售價只能來自釣客這一則訊息；模型不得從行情、常識或前文推測。
- 魚種與處理方式之外的欄位不接受模型自行填入；照片只由上傳事件寫入，官方代碼由後端查詢後填入。
- 釣客一次說出多個欄位時，模型可以一次更新；有模糊數字或聽不出欄位時回問，不改半套。

### 修正告知、修正歷史與可改回

- 修正告知是助手回覆的一部分，顯示在對話中，不另外顯示在草稿卡上。
- 修正告知與下一個問題可以在同一則回覆；多個修正合併成一句，不逐項洗版。
- 每次成功的修正要記錄欄位、原值、新值與時間，放在 conversation context 的修正歷史；修正紀錄只接受魚種與處理方式欄位。
- 釣客可用文字說「改回鬼投刀」或「保留我打的字」；模型依修正歷史把原值寫回，並把該字串加入使用者確認字串。
- 不新增「復原」按鈕；改回一律用對話。
- 後端驗證失敗時不得顯示修正告知；若模型回覆被丟棄，改用規則的安全回覆，避免出現「訊息說改了、草稿沒改」。

### 回應契約與後端驗證

- 助手回覆端點在 listing 模式回傳：回覆文字、修正告知、草稿變更、修正紀錄、新增的使用者確認字串、處理方式縮短提議、處理方式回問計數、下一個動作。
- 草稿變更只接受魚種、尾數、處理方式、整批售價、每台斤售價；官方代碼與照片網址不由模型提供。
- 數字驗證：尾數、整批售價、每台斤售價必須出現在釣客這一則訊息，否則丟棄。
- 魚種修正驗證：原字串查無、修正後唯一候選、原值等於草稿、原字串未被使用者確認；任一不符就丟棄整個模型回覆。
- 處理方式修正驗證：原值等於草稿、編輯距離不超過 2；不符就丟棄。
- 處理方式縮短驗證：草稿變更值必須等於 context 裡的待同意縮短版，且釣客這一則訊息是同意的說法；不符就要求重新確認。提議只在回問計數達兩次時接受，未達兩次時丟棄提議並降級成回問。
- 動作驗證：行情卡只能在非價格欄位完成後顯示；草稿卡只能在全欄位完成後顯示；不符就降級成問問題。
- 模型回覆不得包含發布、下架、刪除、訂單或協議操作；這些仍由既有平台流程處理。
- 模型不直接寫入資料庫；後端只回傳驗證後的變更，前端套用並寫入 conversation context。
- 若模型回覆被驗證丟棄，後端回傳可辨識的「listing 回覆被拒」結果；前端只把該輪交給規則，不顯示修正告知，也不切換基本模式。

### Conversation context

- 新增房間層級的 `basic_mode`，預設 false；切換基本模式後設為 true，開新助手房才重設。
- 新增草稿層級的 `protected_names`、`correction_history`、`condition_proposal`、`condition_ask_count`。
- 舊草稿沒有這些欄位時視為空陣列或 null，不需要資料遷移。
- 這些欄位都很小，不改變現有 context 的 16 KB 上限。
- 不同助手房的草稿、修正歷史與基本模式互不影響。

### 提示詞與工具

- 新增 listing 專用的系統提示詞，職責是：聽懂訊息、更新草稿、套用魚種與處理方式規則、決定下一個問題與卡片時機、產生修正告知；提示詞內容不在本 spec 重複。
- 新增唯讀的官方字典查詢工具，輸入名稱、回傳精確候選（代碼、官方名稱、別名）；只供魚種修正前確認使用，不做模糊比對。
- 模型仍受每輪最多 2 次工具呼叫與既有回覆期限約束；listing 不新增第二次模型呼叫。
- 既有行情、商品搜尋與網路搜尋工具不變；交易房仍不提供任何 LLM 工具。
- 提示詞不得要求模型發布商品、修改已上架商品或繞過後端驗證。

### 介面

- 模型模式：草稿卡只有「確認上架」與「取消上架」；助手在顯示草稿卡時說「想修改直接告訴我」。
- 基本模式：草稿卡恢復「修改草稿」按鈕，使用者回到現行逐欄修改流程。
- AI 故障提示只顯示一次，作為助手訊息；不新增橫幅或設定頁。
- 修正告知使用一般助手文字，不新增卡片型別。
- 發布中的「上架中…」、停用狀態與防重複行為維持不變。
- 鍵盤與螢幕閱讀器行為維持現狀；不新增互動元件。

### 文件

- 新增 ADR，記錄上架草稿改由模型驅動、模型只回傳變更、程式驗證與基本模式；取代 ADR-0011 對上架流程的限制，交易房限制不變。
- 更新 GLOSSARY：改寫「修改草稿」，新增「錯字修正」「使用者確認字串」「基本模式」。
- 更新上架流程與 LLM 助手 spec，補上模型驅動、工具、修正告知、基本模式與按鈕變化。
- 更新資料模型 spec 的 conversation context 欄位。
- 更新 API spec 的助手回覆 listing 契約。
- 更新 UI spec 的草稿卡按鈕與提示。
- 更新 roadmap 的驗收條件。
- 更新 README 與後端 README：`LLM_ENABLED=true` 現在也啟用模型驅動上架；故障時基本模式；草稿欄位本來就會以白名單摘要送給模型。
- 不新增功能旗標文件。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、助手回覆的文字與 context、草稿卡渲染出的按鈕與屬性、發布流程送出的請求。測試不驗私有函式名稱、不驗內部呼叫堆疊，也不為了測試把模組拆得更細。

沿用四個既有斷層，不新增 seam：

1. **後端 HTTP（最高層）**
   - 使用既有測試伺服器、登入 Token、對話與訊息 helper，並用既有 provider 注入點提供假模型。
   - 既有前例：AI 回覆測試、AI 防護測試、AI 工具測試、對話 context 測試。
   - 必測：
     - 模型回傳多欄位草稿變更時，回覆與 context 正確。
     - 合法別名不被修正；模型提出修正也會被後端拒絕。
     - 原字串查無、修正後唯一候選時才套用修正，並產生修正告知。
     - 多候選回問、查無問一次、使用者確認字串阻擋再次修正。
     - 處理方式錯字在編輯距離內才套用；改寫被丟棄。
     - 尾數或售價未出現在釣客訊息時被丟棄。
     - 行情卡與草稿卡的動作時機被程式降級。
     - 模型回覆不含發布操作；交易房不呼叫 LLM。
     - `LLM_DISABLED`、逾時、429、無金鑰的錯誤碼與基本模式判斷。
     - listing 驗證失敗不切換基本模式。
     - 唯讀魚種查詢工具存在、精確比對、回傳代碼與別名。

2. **前端對話流程**
   - 使用既有假 `HaisenAPI`、訊息 factory 與對話流程 helper，直接驅動送出訊息、AI 回覆、套用草稿。
   - 既有前例：AI 回覆流程測試、發布草稿測試、草稿修改測試。
   - 必測：
     - 套用草稿變更與修正告知；context 寫入修正歷史與使用者確認字串。
     - 多欄位修改一次套用；模糊數字回問。
     - 釣客說「保留原字串」後改回，之後同字串不再被修正。
     - 處理方式超過 20 字回問；提議縮短版要釣客同意才套用。
     - 非價格欄位完成後才顯示行情卡；全欄位完成才顯示草稿卡。
     - 草稿卡在模型模式沒有「修改草稿」；基本模式有。
     - 基本模式提示只出現一次、寫入 context、重新載入仍維持。
     - `LLM_DISABLED` 不顯示 AI 故障提示。
     - 確認上架仍只由使用者按鈕觸發；模型回覆不能發布。
     - 發布中的鎖定、停用與防重複行為不退化。

3. **草稿卡渲染**
   - 沿用既有卡片 HTML 測試，不斷言整張卡片 HTML。
   - 必測：
     - 模型模式只有「確認上架」與「取消上架」。
     - 基本模式有三個動作。
     - 發布中狀態仍顯示「上架中…」、三個動作停用、帶 `aria-busy`。

4. **E2E（offline）**
   - 沿用既有助手房 offline 案例，確認 `LLM_ENABLED=false` 時走規則、草稿卡有「修改草稿」、上架流程不退化，且沒有外部 Gemini、Tavily 請求。
   - 不新增 LLM 開啟的 E2E；那需要在正式伺服器加入假 provider 模式，成本高於價值。模型路徑由後端 HTTP 與前端對話流程測試覆蓋。

## Out of Scope

- 買家搜尋的別名展開（另開 issue）；本功能不改商品搜尋、商品名稱或商品列表。
- 錯字模糊搜尋、拼音搜尋、同義詞學習。
- 模型直接發布、下架、刪除、修改已上架商品，或操作訂單、協議、評價。
- 交易房的 AI 回覆。
- 商品描述、行銷文案或自動生成標題。
- 放寬處理方式 20 字限制或只有數字／單位的限制。
- 引入外部學名、生物分類名稱或非官方魚種字典。
- 新增 `LLM_LISTING` 或其他功能旗標。
- 串流回覆、多模態、圖片或語音理解、模型選擇器。
- 自動重試、自動排隊、搜尋結果快取。
- 價格合理性判斷、行情保證或收購價。
- 助手房 UI 改版、草稿卡版面重設、新增設定頁。
- 已上架商品的編輯功能。
- 舊草稿的資料遷移；缺少新 context 欄位時使用預設值即可。

## Further Notes

- 最大的殘餘風險是處理方式的錯字沒有官方字典可驗證；編輯距離上限與釣客可改回是主要防線。
- 魚種修正可能剛好改到另一個合法魚種；官方字典驗證擋不住語意錯誤，靠對話告知與釣客改回補救。
- 商品上架後不能直接改名，只能下架或刪除重上；修正告知必須在釣客按「確認上架」前看到。
- 模型文字每次可能不同；測試要驗欄位、context 與行為，不要驗固定句子。
- 免費層額度有限；每個上架訊息都會呼叫模型，429 時切基本模式，不重試、不排隊。
- listing 回覆與工具呼叫共用既有回覆期限；不新增第二次模型呼叫。
- 所有新增與修改的程式檔案必須維持在 200 行以內；必要時依職責拆分，不要為湊行數硬拆。
- 完成後 `npm test` 應全綠；E2E offline 與快取版本檢查需同步更新。
- 別名搜尋 issue 的需求已另外整理，不在本 spec 內。
