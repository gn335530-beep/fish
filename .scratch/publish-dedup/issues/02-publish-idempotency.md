# 02: 同一份草稿的發布識別碼與後端冪等

**What to build:** 每一份上架草稿帶一組固定的 `client_request_id`，建立商品時一併送出。後端以「釣客＋識別碼」判斷這份草稿是否已經建立過商品：第一次建立回 201；同一個識別碼重送回 200 與第一次相同的商品，不再新增第二筆。識別碼存在商品資料中，但所有商品 API 回應都不外露。修改草稿的魚種、尾數、處理方式、照片或售價不會更換識別碼；發布成功、草稿重設或建立全新草稿後才換新的一組。沒有帶識別碼、空白或格式不合法的舊 client 維持原本可建立多筆商品的行為。

**Blocked by:** 01.

**Status:** resolved

- [x] 新草稿建立時取得一組 `client_request_id`；同一份草稿修改任何欄位後仍沿用同一組。
- [x] 發布成功、草稿重設或建立全新草稿後，下一次發布使用新的識別碼。
- [x] 建立商品請求帶上當下草稿的 `client_request_id`。
- [x] `POST /api/products/create` 由同一釣客帶相同識別碼重送時，第二次回 200 與第一次相同的商品；第一次建立回 201。
- [x] 相同識別碼重送不會新增商品；上架紀錄與公開商品列表都只出現一筆。
- [x] 不同識別碼、沒有帶識別碼、空白或格式不合法的識別碼，維持原本可建立多筆商品的相容行為，且不新增錯誤碼。
- [x] 相同識別碼由不同釣客使用時互不影響，各自建立自己的商品。
- [x] 商品資料保存識別碼，但商品建立、列表、上架紀錄與詳情等 API 回應都不包含它。
- [x] 相同識別碼搭配不同內容時回傳第一次建立的商品，不覆寫、不新增，採 first write wins。
- [x] 商品被硬刪後不保留額外識別碼紀錄；此時同識別碼重送可建立新商品。
- [x] 後端 HTTP 測試涵蓋重送、不同識別碼、缺少識別碼、不同釣客與不合法識別碼；前端流程測試涵蓋識別碼在修改後保持不變，以及失敗重試沿用同一組。
- [x] 修改的程式檔案不超過 200 行。
