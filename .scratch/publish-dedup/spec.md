# 上架確認防重複：即時回饋與冪等建立

**Status:** ready-for-agent

**Source:** 2026-11-15 使用者回報「同樣的商品會容易重複上架，因為確認上架的按鈕沒有回饋，容易按下多次造成重複上架」；2026-11-17 討論後確認採前端鎖定＋後端冪等，並沿用既有 HTTP 與對話流程測試斷層。

## Problem Statement

釣客在助手房填完上架草稿後按「確認上架」，畫面當下沒有任何變化。成功提示要等建立商品、寫入「已上架」訊息、更新對話 context、清除舊訊息全部完成後才出現；在慢網路或後端較慢時，釣客會以為按鈕沒反應而連按好幾次。

每一次點擊都會送出一次建立商品請求，而後端沒有去重，所以同一份草稿會變成多筆商品。釣客在上架紀錄與公開商品列表看到重複項目，買家也可能重複看到同一批漁獲，降低對庫存與價格的信任。

還有一個相關缺口：如果商品其實已建立成功，但後續寫訊息、更新 context 或清除對話失敗，草稿卡會回到可按下狀態；釣客再按一次又會建立第二筆商品。等待期間若切換房間，成功訊息也可能被寫到另一間房。

已經產生的重複商品不會自動消失，仍需釣客自行下架或刪除。

## Solution

- 按下「確認上架」後立即顯示「上架中…」並停用草稿卡的三個動作，讓釣客知道系統已收到點擊。
- 同一時間只允許一筆發布在進行中；重複點擊直接忽略，不送出第二次建立商品請求。
- 每一份草稿帶一組發布識別碼。後端以「釣客＋發布識別碼」判斷是否已經建立過；重送回傳第一次建立的商品，不新增第二筆。
- 發布成功後草稿卡消失，只留下「已上架：{標題}」訊息與 toast。
- 發布失敗時按鈕恢復、草稿保留，並顯示可見的錯誤提示；修正後可安全重試。
- 發布期間切換房間不會影響其他房間；結果只寫回原本送出發布的那一間助手房。
- 新草稿才會有新的發布識別碼；同一份草稿修改魚種、尾數、處理方式、照片或售價後，識別碼不變，重試仍不會重複建立。

## User Stories

1. 作為釣客，我想在按下「確認上架」後立刻看到「上架中…」，以便知道點擊已被系統接收。
2. 作為釣客，我想在發布期間看到三個草稿動作都停用，以便不會再按第二次。
3. 作為釣客，我想連續快速點擊「確認上架」也只建立一筆商品，以便不必擔心手誤。
4. 作為使用慢網路的釣客，我想在等待時安心等系統完成，以便不會因為沒回饋而重複操作。
5. 作為釣客，我想在建立商品的回應遺失後重試，仍然拿到同一筆商品，以便網路不穩不會造成重複上架。
6. 作為釣客，我想在建立成功但後續步驟失敗時重試，仍然不會多出第二筆，以便部分失敗也能安全復原。
7. 作為釣客，我想在發布失敗時看到明確錯誤，以便知道這次沒有成功。
8. 作為釣客，我想在發布失敗後看到草稿與按鈕恢復，以便修正後直接重試。
9. 作為釣客，我想在發布成功後只看到「已上架：{標題}」，以便知道草稿已結束。
10. 作為釣客，我想在發布成功後看到包含商品標題的 toast，以便快速確認上架內容。
11. 作為釣客，我想在發布前修改草稿欄位而不改變發布識別碼，以便修改後重試仍不會重複建立。
12. 作為釣客，我想在發布成功後再開一份新草稿時取得新的發布識別碼，以便日後可以刻意再上架一批相同的魚。
13. 作為釣客，我想在發布期間切換到別的助手房後，結果仍然留在原本那一間，以便不會污染另一間對話。
14. 作為釣客，我想讓不同助手房的草稿各自獨立，以便其中一間的發布狀態不會影響另一間的草稿內容。
15. 作為使用鍵盤或螢幕閱讀器的釣客，我想在發布期間取得 `aria-busy` 與停用狀態，以便知道系統正在處理。
16. 作為買家，我想在公開商品列表只看到一筆真正的上架批次，以便不會把重複項目誤認為還有更多庫存。
17. 作為買家，我想在助手房的商品結果看到去重後的商品，以便推薦內容值得信任。
18. 作為釣客，我想在上架紀錄只看到一筆這次發布，以便管理商品時不必手動刪除重複項。
19. 作為釣客，我想在遇到既有重複商品時仍能從上架紀錄下架或刪除，以便清理舊資料。
20. 作為改版前就已建立草稿的釣客，我想至少仍有前端防連點，以便這次修正不會讓舊草稿完全沒有保護。
21. 作為維護者，我想用「釣客＋發布識別碼」查重，以便不同釣客剛好使用相同識別碼時不會互相影響。
22. 作為維護者，我想讓空白或格式不合法的識別碼視為沒有帶，以便舊頁面與舊 client 維持原本行為。
23. 作為維護者，我想把識別碼存在商品資料中但不從商品 API 回傳，以便內部防重複機制不外洩。
24. 作為維護者，我想讓同一個識別碼搭配不同內容時回傳第一次建立的商品，以便重送永遠是 first write wins，不會覆寫或新增。
25. 作為維護者，我想讓第一次建立回 201、重送回 200，以便測試與 API 行為可清楚區分。
26. 作為維護者，我想在商品被硬刪後不再保留識別碼，以便不引入隱藏紀錄；此時同識別碼重送會建立新商品。
27. 作為維護者，我想沿用既有 HTTP 測試與對話流程測試斷層，以便不新增測試框架或第二套 API stub。
28. 作為維護者，我想在測試中驗證重送、不同識別碼、不同釣客與沒有識別碼的情境，以便防重複行為有完整回歸保護。
29. 作為維護者，我想讓草稿卡 HTML 測試驗證「上架中…」與停用狀態，以便 UI 回饋不會退化。
30. 作為維護者，我想更新相關規格、後端 README 與快取版本，以便文件、程式與部署後行為一致。
31. 作為維護者，我想讓所有修改檔案維持在 200 行以內並讓 `npm test` 通過，以便符合專案規範。

## Implementation Decisions

### 前端發布狀態

- 共用狀態新增 `publishing` 布林值，預設 `false`。
- `publishDraft()` 在任何 `await` 之前同步設為 `true`；若已在進行中則立即返回，不送出任何請求。
- 不論成功或失敗，都以 `finally` 設回 `false`，失敗時草稿卡恢復可操作。
- 同一時間只允許一筆發布。進行中時所有可見草稿卡都顯示忙碌狀態，避免使用者在切房後看到可點但實際被忽略的按鈕。
- 草稿卡忙碌狀態：
  - 主要按鈕文字改為「上架中…」。
  - 「確認上架」、「修改草稿」、「取消上架」全部加上 `disabled`。
  - 卡片或主要按鈕加 `aria-busy="true"`。
  - 樣式沿用既有草稿卡，只新增停用外觀；不改變卡片版面與其他欄位。
- 發布成功維持現有結果：寫入「已上架：{標題}」、重設草稿 context、清除舊訊息、替換成只剩該則訊息，並顯示 toast。
- 發布失敗除了既有面板提示外，再顯示一次 toast，確保錯誤在訊息流底部也看得到。
- 發布開始時先捕獲 `roomId` 與當下 context。建立商品、寫訊息、更新 context、清除訊息全部使用捕獲的 `roomId`。
- 只有目前檢視仍停在該 `roomId` 時，才更新 `state.room` 與替換目前訊息；切到別房時不得改動該房訊息。
- 草稿卡需要的忙碌狀態由既有訊息渲染路徑傳入；不讓卡片模組直接讀取全域狀態。

### 草稿發布識別碼

- 草稿建立時產生一組不透明的 `client_request_id`，存進草稿資料。
- 修改草稿沿用既有草稿物件合併，識別碼因此保持不變。
- 發布成功、草稿重設或建立全新草稿時才取得新的識別碼。
- 建立商品時把草稿的 `client_request_id` 一併送出。
- 草稿卡不顯示這個欄位；它只是內部發布識別碼。
- 改版前已存在且沒有識別碼的草稿不強制補值；這類草稿仍保有前端防連點，但不保證跨重新整理的重試能由後端去重。

### API 契約

- `POST /api/products/create` 新增可選的 `client_request_id`。
- 合法值為 1–80 個英數字、底線或連字號；空白、超長或含其他字元時視同沒有帶，不新增錯誤碼。
- 後端先以 `seller_id`＋`client_request_id` 查詢既有商品：
  - 找到：回 200，`data` 為第一次建立的商品，訊息為「商品已上架」，不新增資料。
  - 找不到：照既有驗證與建立流程處理，成功回 201。
- 查重發生在其他欄位驗證之前；同一個識別碼重送時，即使請求內容有細微差異，也回傳第一次建立的商品。
- 沒有帶識別碼時完全維持現行行為，可建立多筆相同內容的商品。
- 不以「同釣客＋相同魚種／數量／價格」等內容啟發式去重，避免誤擋刻意再次上架。
- 回應中的商品一律不包含 `client_request_id`。

### 資料模型

- `products` 新增內部欄位 `client_request_id`（string 或 null）。
- 既有商品不需要遷移；缺少此欄位視為 null。
- 商品被硬刪後，識別碼紀錄也消失；之後同識別碼重送會建立新商品。
- 沒有新增 collection、counter 或背景清理工作。

### 快取版本

- 修改草稿卡樣式後，所有載入該樣式的頁面把 `deal-cards.css` 從 `v9` 升到 `v10`，跨頁版本一致。
- 助手前端模組有變更，所有載入頁面的 `main.js` 從 `v17` 升到 `v18`。
- 快取版本 e2e 檢查把 `deal-cards.css` 的最低版本提高到 `v10`。
- 不改其他未修改資產的版本。

### 文件

- `docs/spec/03-flows.md`：F2 步驟 12 補上按下後立即鎖定、重複點擊不重複建立，以及重送回傳同一商品。
- `docs/spec/04-data-model.md`：`products` 新增內部 `client_request_id`，並註明不外露。
- `docs/spec/05-api.md`：建立商品 API 新增可選欄位、200／201 行為、first write wins 與錯誤碼不變。
- `docs/spec/06-ui.md`：草稿卡新增「上架中…」、停用三個動作與錯誤回饋。
- `docs/spec/07-roadmap.md`：補一條連點上架只會產生一筆商品的驗收條件。
- `backend/README.md`：建立商品端點加註冪等行為。
- `GLOSSARY.md` 不需新增名詞；這是既有「上架草稿」與「商品」的行為修正。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、對話發布流程送出的請求、發布後的訊息與 context、草稿卡渲染出的文字與屬性。測試不驗私有函式名稱、不驗內部呼叫堆疊，也不為了測試把模組拆得更細。

沿用三個既有斷層，不新增 seam：

1. **後端 HTTP（最高層）**
   - 使用既有測試伺服器、登入 Token 與商品建立 helper。
   - 既有前例：商品建立測試、商品生命週期測試。
   - 必測：
     - 同一釣客帶相同 `client_request_id` 重送兩次：第一次 201、第二次 200，商品 ID 相同，上架紀錄只有一筆，回應不含 `client_request_id`。
     - 不同 `client_request_id`：兩筆商品。
     - 沒有 `client_request_id`：兩筆商品，維持舊行為。
     - 相同 `client_request_id`、不同釣客：各自建立一筆，互不影響。
     - 空白或格式不合法的識別碼：視同沒有帶，正常建立。

2. **前端發布流程**
   - 使用既有假 `HaisenAPI` fixture 與訊息 factory，直接驅動發布流程；既有前例是 AI 回覆流程測試。
   - 必測：
     - 連續呼叫兩次發布只送出一次建立商品請求。
     - 發布進行中時草稿卡 HTML 顯示「上架中…」且三個動作都有 `disabled`。
     - 發布失敗後 `publishing` 恢復、草稿保留、錯誤提示被呼叫。
     - 第一次失敗後重試，送出的 `client_request_id` 與第一次相同。
     - 修改草稿欄位後再發布，識別碼不變；建立新草稿時識別碼不同。
     - 發布期間切換房間，建立商品與「已上架」訊息仍屬於原本房間，目前房間的訊息不被替換。

3. **草稿卡渲染**
   - 沿用既有 `renderCard` HTML 字串測試，不斷言整張卡片 HTML。
   - 必測：
     - 一般狀態顯示「確認上架」，三個動作沒有 `disabled`。
     - 忙碌狀態顯示「上架中…」、三個動作都有 `disabled`，並帶 `aria-busy`。
     - 忙碌狀態不顯示「確認上架」按鈕文字，避免兩個標籤同時出現。

不新增 Playwright 連點案例；快取版本 e2e 只更新既有鎖定版本。發布行為由 Node 測試覆蓋，視覺外觀沒有新增版面。

## Out of Scope

- 不自動刪除或合併已經存在的重複商品；仍由釣客從上架紀錄處理。
- 不以內容相似度去重；只認明確的 `client_request_id`。
- 不為改版前的舊草稿回填識別碼，也不保證舊草稿在重新整理後的重試能由後端去重。
- 不處理其他端點或其他卡片動作的冪等與忙碌狀態，例如法規確認、取消上架、下架、重新上架。
- 不改草稿修改、取消上架、商品建立驗證、商品狀態或訂單流程。
- 不新增 ADR 或 glossary 名詞；這是可逆的防重複修正。
- 不新增獨立的發布請求 collection，也不做事後清理。
- 不新增 Playwright 連點或慢網路案例。
- 不改商品照片、價格、庫存、列表排序或交易房 UI。

## Further Notes

- 已產生的重複商品仍可從上架紀錄下架後刪除；本次只防止新的重複。
- 舊草稿沒有識別碼時，前端鎖仍可阻擋同一個 tick 與同一次瀏覽階段的連點，但無法保證跨重新整理的重試。
- 商品硬刪後識別碼也消失；若日後用同一份草稿重送，會建立新商品。這是刻意選擇，避免額外保存已刪除商品的紀錄。
- 同識別碼重送會回傳第一次建立的商品，即使該商品後來已下架或售完；對使用者而言仍是「已上架」，不會產生第二筆。
- 這是缺陷修正，不新增使用者可見的設定或文案頁面；主要新增文案只有「上架中…」與失敗 toast。
- 所有修改與新增檔案必須維持在 200 行以內。
- 完成後 `npm test` 應全綠；快取版本 e2e 需同步更新。
