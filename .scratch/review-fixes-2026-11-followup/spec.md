# Review 收尾：CSS 單一來源、行情卡縮放與文件對齊

**Status:** ready-for-agent

**Source:** 2026-11-10 對 `6399071...HEAD`（3 個 commit）的 Standards／Spec 雙軸 review；延伸 `.scratch/review-fixes-2026-11/` 的 8 張 ticket。

## Problem Statement

買家與釣客目前看到的畫面大致正確，但這批 review 修正留下幾個會讓下一次改動出錯的尾巴。

- 商品卡照片比例同時存在 `4/5` 與 `3/2` 兩條規則；`4/5` 已被覆蓋，仍是 dead CSS。維護者改比例時必須先猜哪一條生效。
- 聊天面板的外框、標題列與頁尾同時由兩個樣式模組定義；載入順序是行為的一部分，改一邊可能被另一邊蓋掉。
- 行情卡價格的垂直縮放值 `.9` 還留在 CSS，沒有跟水平縮放常數放在一起；改字級或卡片可用寬度時容易漏改。
- 四個已修改的樣式模組仍使用舊的 `?v=` 版本。部署後若前面有 CDN 或長快取，回訪買家可能拿到舊樣式，看不到修正後的卡片與面板。
- UI 規格寫「近 N 交易日」，實際畫面是「近7個交易日」；交易房 spec 的商品條、發送交易與加購章節沒有同步「處理方式（若有）」。實作者與 agent 會得到互相矛盾的指示。

這些不是新功能，而是維護性、文件與部署快取的問題。使用者要的結果是：畫面與行為不變，但下一次改動只需要改一個地方。

## Solution

做一輪無視覺變化的收尾。

- 商品卡照片比例只留 `3:2` 一個來源；移除被覆蓋的 `4/5`。
- 聊天面板外殼只由一個樣式模組負責；另一個模組只留浮動開啟鈕與自身職責。
- 行情卡的水平與垂直縮放常數集中到同一個地方；CSS 只消費自訂屬性，不寫死 `.9`。
- 四個已修改的樣式模組更新 `?v=`，三個頁面同步。
- UI 規格與交易房 spec 對齊實際文案與共用商品摘要：魚種、處理方式（若有）、`剩 N 尾`、每台斤或整批價格。
- 保留 `AGENTS.md` 的文件同步章節，明確認可這是刻意的治理變更，不是漏掉的 scope。
- 以 Playwright 視覺 seam 驗證三個頁面、行情卡 7／30 日與交易房面板的幾何與關鍵狀態；既有 Node 測試維持回歸保護。

## User Stories

1. 作為回訪買家，我想在部署後取得新樣式，以便修正後的卡片與面板真的出現在我的瀏覽器。
2. 作為買家，我想在首頁、商品列表與登入頁看到一致的聊天面板外框，以便切換頁面時不會看到不同形狀。
3. 作為買家，我想在手機與桌機看到一致的面板尺寸規則，以便開啟助手房時不跳版。
4. 作為買家，我想在商品卡看到 `3:2` 的照片框與完整照片，以便照片不被裁切。
5. 作為買家，我想在商品卡照片留白時看到模糊底圖，以便視覺仍然完整。
6. 作為買家，我想在行情卡 7 日與 30 日切換時看到「近7個交易日」與「近30個交易日」，以便知道圖表區間。
7. 作為買家，我想在行情卡看到價格與「元/台斤」不重疊，以便長價格也能讀。
8. 作為買家，我想在行情卡看到交易日期與來源固定在原本位置，以便快速確認資料新鮮度。
9. 作為買家，我想在行情卡看到重量試算與參考價不因這次收尾而改變，以便估價一致。
10. 作為買家，我想在交易房看到浮動商品條，以便知道目前訂單草稿。
11. 作為買家，我想在商品條每列看到魚種、處理方式（若有）、`剩 N 尾` 與每台斤或整批價格，以便確認要買什麼。
12. 作為買家，我想在發送交易面板看到與商品條相同的摘要，以便送出的內容與我選的一致。
13. 作為買家，我想在加購面板看到同樣的摘要且不顯示 legacy 重量，以便不會被舊資料混淆。
14. 作為買家，我想在協議卡看到魚種、數量、最終價格、面交時間與地點，以便確認交易。
15. 作為釣客，我想在規格文件看到與畫面相同的商品摘要欄位，以便上架與回覆買家時用同一套語言。
16. 作為釣客，我想在交易房看到面板展開後取代商品條，以便畫面不會同時出現兩層。
17. 作為維護者，我想讓商品卡比例只有一個來源，以便改 `3:2` 時不用追兩條規則。
18. 作為維護者，我想讓聊天面板外殼只有一個來源，以便改圓角、陰影或尺寸時只改一處。
19. 作為維護者，我想讓行情卡水平與垂直縮放常數放在同一個地方，以便改字級或可用寬度時不會漏掉 `.9`。
20. 作為維護者，我想讓行情卡 CSS 只讀變數、不寫死縮放值，以便程式與樣式不會各自漂移。
21. 作為維護者，我想讓四個改過的樣式模組都帶新版本，以便部署快取不會讓修正失效。
22. 作為維護者，我想讓 UI 規格用「近 7／30 個交易日」而不是模糊的「近 N 交易日」，以便文件可被直接實作。
23. 作為維護者，我想讓交易房 spec 的商品條、發送交易與加購章節都列出處理方式（若有），以便三個地方不會再次漂移。
24. 作為維護者，我想把只用一次的行情問答包裝函式內聯，以便閱讀流程時少一層跳轉。
25. 作為維護者，我想保留 `AGENTS.md` 的文件同步章節並記錄原因，以便未來改動仍會同步文件。
26. 作為審查者，我想用 Playwright 在真實瀏覽器看到三個頁面與行情卡 7／30 日的幾何，以便確認這次是無視覺變化。
27. 作為審查者，我想用一個指令跑視覺測試，以便不再只靠肉眼。
28. 作為 agent 實作者，我想在 spec 看到明確的 Out of Scope，以便不會順手重做視覺設計。
29. 作為使用者，我想在行情卡查無資料時仍看到「暫無行情」，以便這次收尾不改動錯誤狀態。
30. 作為使用者，我想在商品已下架或售出時仍看到原本的狀態文案，以便這次收尾不改動生命週期行為。

## Implementation Decisions

### CSS 單一來源

- 商品卡照片：只有 catch-card 照片模組擁有 `3:2`。base card media 不再宣告 `4/5`；若 base 的 position、background、overflow 只被 catch-card 使用，一併移到 catch-card 模組，讓 base 不再保留 dead 屬性。
- 聊天面板：`chat-frame`（外殼）擁有面板、標題列、內文區與頁尾的尺寸、圓角、背景、陰影、grid、overflow 與 transition。`deal-bot` 只留浮動開啟鈕、badge、bot 容器與手機版開啟鈕定位。
- 面板外殼不再依賴兩個模組的載入順序。若某頁需要變體，使用 modifier class，不重複同一個 selector 的同一組屬性。
- `chat-bubbles` 只負責訊息氣泡、空狀態與收件匣，不重複面板外殼尺寸。
- 合併後若單一檔案超過 200 行，依「外殼」與「內容」職責拆檔，不壓縮程式碼。

### 行情卡縮放

- 價格幾何常數集中為一個凍結常數，包含字寬、可用寬度、最小水平縮放與垂直縮放；垂直縮放就是目前的 `.9`。
- 行情卡渲染時，價格元素同時輸出水平與垂直縮放的自訂屬性。
- CSS 只讀這兩個自訂屬性；不再出現 `.9` 字面值，也不把垂直縮放散落到其他 selector。
- 不改 48px 字級、可用寬度、價格文字、卡片座標或 7／30 日切換行為。
- 若沒有 inline style 的舊 markup 仍可能存在，CSS 的預設值要與常數一致，並由測試鎖定；不要讓預設值成為第二個來源。

### 快取版本

- 本次修改的樣式模組（layout、product-card-photo、components、deal-bot、deal-cards）在首頁、商品列表與登入頁統一提版；layout 與 product-card-photo 已在 ticket 03 提版，其餘由 ticket 07 處理。
- 版本字串只遞增，不改檔名；三個頁面必須使用相同版本。
- 不要為所有靜態資產建立版本清單；只鎖定本次五個模組，避免未來每次升版都要改測試。

### 文件

- UI 規格的行情小卡日期行改為「近 7／30 個交易日」，與程式輸出的「近7個交易日／近30個交易日」一致；文件描述區間，不逐字鎖定空白。
- 交易房 spec 的浮動商品條、發送交易與加購章節補上「處理方式（若有）」與共用摘要；購物車章節若已更新則保持一致。
- 領域、流程與 API 規格只檢查是否已有同樣欄位，不新增 API、不改 schema。
- `AGENTS.md` 的文件同步章節保留；在 Further Notes 記錄它是本次 review 的刻意治理變更。

### 程式小清理

- 行情問答中只包一個欄位、且只用一次的包裝函式，以及只轉呼叫的輔助函式，若內聯後流程更短且既有行情問答測試不變，就內聯。
- 若內聯會讓流程更難讀，保留並加註解；此項是 low priority，不阻塞其他工作。
- 不改行情查詢流程、候選魚種回問、查無行情或 API 錯誤處理。

### 邊界與既有決策

- 不改 API、不改 schema、不改 ADR。
- 行情卡仍只顯示平均價、交易日期、來源；商品卡仍不顯示行情（ADR 0007）。
- 商品生命週期與訂單狀態機不變（ADR 0009）。
- 所有被修改的程式碼檔案維持 200 行以下。

## Testing Decisions

### Seam

主要新增一個 Playwright browser seam，測試使用者在真實瀏覽器看到的外部行為。既有 Node 測試維持單元與渲染層回歸；不新增 CSS 文字契約測試，也不把 Playwright 塞進 `npm test`。這樣只有一個新的高階 seam，且沒有瀏覽器的環境仍可跑既有測試。

### 什麼是好測試

- 只斷言使用者可觀察的結果：元素是否存在、文字、bounding box 幾何、computed style 的關鍵值、是否溢出或重疊。
- 不斷言 CSS 檔內容、selector 位置、內部函式名稱或檔案行數；那些是實作細節。
- 視覺快照只用在穩定狀態，並固定 viewport、`deviceScaleFactor: 1`、停用動畫、等待 `document.fonts.ready`。若字型或平台造成不穩，優先改用幾何與 computed style 斷言，不要把 threshold 放寬到失去意義。
- 每個案例都要能在沒有上游行情 API 的情況下重現；行情卡用固定資料，不打真實批發行情。
- 視覺 baseline 以改動前的頁面截圖為準。若先改程式才建立 baseline，必須回到固定點重新截圖比對，避免把回歸畫成新基準。

### 測試環境

- 用既有的靜態前台伺服器啟動前台，用測試用資料庫啟動後端；Playwright 設定一次啟動兩者，測試結束關閉。
- 登入流程使用 seed 的買家帳號；交易房測試使用 seed 的對話與商品。若 seed 沒有穩定的行情卡訊息，使用真實的行情卡 view 加固定資料注入頁面，不改產品流程。
- 固定 viewport：桌機 1280×800、手機 390×844；語系 `zh-TW`、時區 `Asia/Taipei`。
- 只跑 chromium 作為必要案例；其他瀏覽器可選，不阻塞合併。

### 測試模組與案例

1. **三個頁面（首頁、商品列表、登入）**：桌機與手機都沒有水平溢出；聊天面板開啟後的尺寸、圓角、背景與關閉狀態一致；商品卡照片框比例為 `3:2`，照片完整顯示。
2. **行情卡**：7 日與 30 日、短價格與長價格；價格 bounding box 不與「元/台斤」重疊、不超出卡片；交易日期與來源在原本區域；重量試算與參考價仍可互動。
3. **交易房**：浮動商品條每列有魚種、處理方式（若有）、`剩 N 尾`、每台斤或整批價格；展開發送交易或加購面板後取代商品條；摘要與商品條一致；加購列沒有重量。
4. **快取版本**：三個頁面的本地 CSS／JS 請求都有 `?v=`；本次四個樣式模組不再使用舊的 `v8`，且三個頁面版本一致。
5. **文件**：不由 Playwright 測；以 review checklist 確認 UI 規格與交易房 spec 的章節用語一致。

### 指令與 CI

- `npm test` 保持現有 Node 測試。
- 新增 `npm run test:e2e` 跑 Playwright；CI 可先只跑 chromium。
- Playwright 設定與測試檔也受 200 行限制；過長時依「頁面案例」拆分。

### Prior art

- 首頁靜態測試已用檔案 artifact 斷言鎖定行數與文案。
- 行情卡渲染測試已用 HTML 字串斷言鎖定使用者可見文案。
- 面板 shell 測試已用 markup 斷言鎖定標題列、頁尾與外殼結構。
- 商品卡測試已用瀏覽器腳本 context 鎖定商品卡 HTML。
- Playwright 沿用同樣的「使用者看到什麼」斷言風格，而不是整頁 snapshot。

## Out of Scope

- 不改任何視覺設計、排版、配色、字級、卡片座標或互動流程。
- 不改行情 API、行情來源、快取策略、商品生命週期、訂單或協議狀態機。
- 不改商品卡照片比例（維持 `3:2`）、不改行情卡來源行位置（維持右下）、不改聊天室訊息區底色（維持 `paper-2`）。
- 不把卡片專用色值統一成 `--accent`；不重做行情卡背景 SVG 的色票，因為它是 CSS background image，CSS 變數無法套用。
- 不新增 ADR；這是無架構變更的收尾。
- 不處理本批 review 未列出的新功能或視覺重設計。
- `marketMeta`／`priceReply` 的內聯是 low priority；若會降低可讀性可以不做。

## Further Notes

- 完成標準是「畫面與行為不變、`npm test` 通過、Playwright 視覺案例通過、文件與程式一致」。
- `AGENTS.md` 的「文件同步」章節是刻意保留的治理變更，不是 scope creep；若團隊決定回退，單獨一個 commit 處理，不混進本批。
- 行情卡背景 SVG 仍保留硬寫色值；若未來要 tokenize，必須先改成 inline SVG 或改用 CSS mask，這是另一個視覺決策。
- 文件與程式不一致視為缺陷。若實作時發現 spec 與實際畫面有第三種說法，先停下來更新 spec，再改程式。
- 新增 Playwright 會多一個 devDependency 與瀏覽器安裝步驟；這是本次選擇視覺 seam 的刻意代價，換取 CSS cascade 與面板幾何的真實驗證。
