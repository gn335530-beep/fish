# 18: 逾時掃描補齊

**What to build:** 系統在讀取對話清單與訂單時也會掃描進行中的訂單，不只商品端點。待回覆超過 30 分鐘或協商中超過 15 分鐘的訂單自動取消、釋放保留尾數、協議卡轉為已逾時，並在交易房留下系統訊息。（規格：R-11、F8）

**Blocked by:** 17（同意、退回、取消與成交）

**Status:** resolved

- [x] 把待回覆訂單的鎖定時間調到過期後，讀取對話清單就會觸發取消。
- [x] 把協商中訂單的保留時間調到過期後，讀取訂單或對話清單就會觸發取消。
- [x] 逾時取消後保留尾數立即釋放，商品可售尾數與狀態正確。
- [x] 協議卡狀態顯示已逾時，交易房有系統訊息說明原因。
- [x] 重複掃描不會重複取消或重複寫入系統訊息。

## Comments

- 2026-10-25：`GET /api/conversations` 與 `GET /api/deals/:id` 在讀取前呼叫 `sweepExpired()`；逾時訂單轉 `CANCELLED`、原因 `LOCK_EXPIRED`／`HOLD_EXPIRED`、清空 `lock_expires_at`／`hold_expires_at`、更新 `updated_at`，最新協議卡轉 `expired` 並插入系統訊息。因為狀態離開進行中，保留尾數立即由衍生計算釋放。
- 2026-10-25：寫入端點（`propose`、`respond`、`cancel`）也會先掃描，避免舊畫面在逾時後仍能同意或重送。系統訊息寫入時統一更新對話的 `last_message_at`，逾時取消的房間也會排到清單最前面。
- 2026-10-25：掃描只處理 `PENDING_REVIEW`／`NEGOTIATING`；轉為 `CANCELLED` 後不會再被掃到，重複讀取不會重複取消或重複留言。
- 2026-10-25：新增 `backend/test/deal-timeout.test.js`（5 個案例：對話清單觸發、重複掃描、訂單讀取觸發、未逾時不受影響、未經讀取也不能同意逾時協議）。前端協議卡本來就會把 `expired` 顯示為「已逾時」，另補了一個沒有動作的測試。
