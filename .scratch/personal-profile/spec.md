# 個人資訊與設定頁

**Status:** ready-for-agent

**Source:** 2026-11-10 對話、`D:\專題\卡片\個人頁.svg` 區塊草圖，以及既有交易房、評價、商品與會員程式。

## Problem Statement

目前沒有公開的個人資訊頁。使用者只能看到自己的右側抽屜，內容是頭像、暱稱、電話與交易／上架紀錄；別人的頭像、地區、商品與評價都無法從商品卡或交易房找到。商品卡上的「賣家資訊」按鈕只有 markup，沒有任何行為。

同時，評價在資料上雖然是雙向的，卻只有一份混合的平均星等。買家無法分辨一個人是「當釣客的評價」還是「當買家的評價」；交易房標題列也只能顯示混合平均，買家看到的不是對方作為釣客的信用。

頭像只存在目前瀏覽器的 `localStorage`，公開頁無法取得別人的頭像。電話是登入帳號，但設定頁只能唯讀；地址也沒有編輯入口。

使用者要的是一個公開的**個人資訊**頁：買家與釣客都能查看，顯示頭像、名字、商品與評價；自己的編輯入口改成獨立的**設定**頁。評價要依方向分開，商品照片要用在評價卡上；「聊聊」要能從個人資訊開交易房，購物車可以加入與移除商品。

## Solution

- 新增公開個人資訊頁，顯示頭像、名字、地區、成交數、驗證標章、角色別評分、商品與評價。
- 新增獨立設定頁，編輯頭像、暱稱、電話、縣市、區與地址；電話可修改，不需目前密碼，也不強制重新登入。
- 評價依 `reviewer_role` 分成「買家給的評價」與「釣客給的評價」，各自有平均分、分布、排序、星等篩選與分頁；預設顯示買家給的評價（釣客的評價），沒有才切到釣客給的評價。
- 評價卡使用該筆成交訂單的商品快照照片，最多 3 張，不連商品頁、不做 lightbox。
- 自己的個人資訊頁顯示全部商品（上架中／已下架／已售出），可用「管理商品」切換成「完成」，並在卡片上操作下架、重新上架與刪除；別人的頁面只顯示可購買商品。
- 「聊聊」從個人資訊開交易房：對方有商品時建立或沿用空購物車；沒有商品時只純聊天、不顯示浮動購物車。房間方向固定為「按聊聊的人＝買家、被看的人＝釣客」；反向交易是另一間房。
- 購物車可加購、逐項移除、直接改數量；不做清空全部；移除不留系統訊息。
- 導覽列「我的」改成個人資訊、設定、交易紀錄、上架紀錄、登出；抽屜只保留交易紀錄與上架紀錄。

## User Stories

1. 作為買家，我想從商品卡的「釣客資訊」打開對方的個人資訊，以便在購買前認識對方。
2. 作為買家，我想在個人資訊看到頭像、名字、地區、成交數與驗證標章，以便判斷對方是否可信。
3. 作為買家，我想看到對方作為釣客的評價，以便判斷要不要交易。
4. 作為釣客，我想看到對方作為買家的評價，以便判斷這筆交易是否值得接。
5. 作為使用者，我想在對方同時是買家與釣客時看到兩種評價，以便分開判斷兩個角色。
6. 作為使用者，我想預設看到買家給的評價（釣客的評價），以便先看最重要的信用。
7. 作為使用者，我想在沒有買家給的評價時自動切到釣客給的評價，以便頁面不會空著。
8. 作為使用者，我想看到評價的平均分、星等、總數與 5→1 分布，以便快速掌握評價結構。
9. 作為使用者，我想用最新、最高、最低排序評價，以便找到我想看的內容。
10. 作為使用者，我想點分布長條篩選星等，以便只看 1 星或 5 星。
11. 作為使用者，我想一次載入 6 則並按「載入更多」，以便讀完所有評價。
12. 作為使用者，我想在評價卡看到評價者的頭像與名字，以便知道是誰寫的。
13. 作為使用者，我想點評價者名字連到他的個人資訊，以便查對方的信用。
14. 作為使用者，我想在評價卡看到星等、日期、標籤與評語，以便了解交易經驗。
15. 作為使用者，我想在評價卡看到該筆訂單的商品照片，以便知道評價對應什麼商品。
16. 作為使用者，我想一筆訂單有多個商品時最多看到 3 張照片與 `+N`，以便卡片不會過長。
17. 作為使用者，我不想在評價卡點照片開新頁或 lightbox，以便閱讀不被打斷。
18. 作為使用者，我想在沒有評價時看到「尚無評價」，以便知道不是載入失敗。
19. 作為使用者，我想在對方只有買家或只有釣客身分時只看到一種評價，以便畫面不誤導。
20. 作為使用者，我想在評價載入失敗時看到錯誤與重試，以便知道如何處理。
21. 作為使用者，我想在手機上看到單欄評價與商品，以便在小螢幕閱讀。
22. 作為使用者，我想在公開個人資訊只看到地區，不要電話與地址，以便保護隱私。
23. 作為使用者，我想在個人資訊看到對方目前可購買的商品，以便直接挑選。
24. 作為買家，我想在商品卡按「洽談購買」開交易房，以便從個人資訊直接購買。

## Implementation Decisions

### 1. 名詞與頁面

- 公開頁叫**個人資訊**；自己的編輯頁叫**設定**。兩者是不同頁面，不再把「個人資訊」當成抽屜內的編輯區。
- 個人資訊頁的網址帶使用者 id；別人的頁面與自己的頁面使用同一個畫面，只有動作不同。
- 自己的頁面：主要動作是「編輯個人資訊」；別人的頁面：主要動作是「聊聊」。
- 公開頁不顯示電話、地址、銀行資料與 `username`。
- 設定頁需登入；未登入導到登入頁。
- 導覽列「我的」順序：個人資訊（自己的公開頁）、設定、交易紀錄、上架紀錄、登出。
- 個人抽屜只保留交易紀錄與上架紀錄；抽屜內的個人資訊編輯區移除。抽屜標題的頭像與名字可連到自己的個人資訊。
- 商品卡的「賣家資訊」改名「釣客資訊」，改成連到個人資訊；推薦小卡仍然沒有這個按鈕。
- 評價者頭像／名字、交易房標題列對方名字都連到個人資訊。

### 2. 個人資訊頁

版面順序：

1. 標題列：頭像、名字、角色別評分 chips、地區、成交筆數、驗證標章；右側動作按鈕。
2. 商品區：標題、商品數量、管理模式切換、商品卡 grid。
3. 評價區：角色 tabs（需要時）、摘要、分布、排序、評價卡、載入更多。

標題列規則：

- 頭像：後端 `avatar_url`；沒有時顯示名字首字，沿用現有 `.avatar` 樣式。
- 名字：`display_name`。
- 地區：`region`；沒有時不顯示。
- 成交筆數：`completed_deals`；顯示「成交 N 筆」。
- 驗證標章：`is_verified` 為真時顯示。
- 評分 chips：只顯示有評價的角色；順序固定為「買家給的評價」在前、「釣客給的評價」在後。只有一種就顯示一個；沒有就「尚無評價」。
- 自己的頁面：按鈕「編輯個人資訊」→ 設定頁。
- 別人的頁面：按鈕「聊聊」；未登入導到登入頁；自己不能對自己按聊聊。

商品區：

- 別人的頁面：`GET /api/products?seller_id=`，只會拿到 `ACTIVE`／`PARTIALLY_RESERVED`；顯示可購買商品卡。
- 自己的頁面：`GET /api/products/mine`，顯示全部未刪除商品（上架中／洽談中／已售出／已下架）。
- 商品卡沿用現有直式卡；個人資訊頁隱藏「釣客資訊」。
- 別人的頁面：可購買商品顯示「洽談購買」；不可購買時沿用「洽談中，暫無法購買」或「已售出」。
- 自己的頁面：不顯示「洽談購買」；正常模式只顯示狀態徽章，管理模式顯示管理動作。
- 空狀態：別人的頁面「目前沒有上架商品」；自己的頁面「你還沒有上架商品」。
- 商品數量多時使用 grid 換行，不做橫向捲動。

評價區：

- 角色 tabs 只在兩種評價都存在時出現；只有一種時直接顯示該種，不顯示 tab。
- 預設 tab：買家給的評價（釣客的評價）。若買家給的評價為 0，預設釣客給的評價。兩者都為 0 顯示空狀態。
  - 本 spec 的「釣客評價優先」定義為「該使用者作為釣客的評價」（買家給的評價）優先；不是「釣客給出的評價」優先。所有文件與 UI 文案都用完整標籤，避免再用簡寫。
- 每個 tab 各自有：平均分＋星等＋總數、5→1 分布、排序選單、星等篩選、評價卡、載入更多。切換 tab 不影響另一個 tab 的排序與篩選，但重新載入頁面可回到預設。
- 分布長條可點擊篩選星等；點擊後列表只顯示該星等，分布本身仍顯示全部。
- 分布少於 3 則時只顯示摘要與列表，不顯示分布，避免比例失真。
- 排序：最新（預設）、最高、最低。
- 每頁 6 則；載入更多以 offset 累加。
- 評價卡：評價者頭像（fallback 首字）、名字（連個人資訊）、日期、星等、標籤、評語、商品照片。
- 商品照片：從該筆評價的訂單項目快照取 `photo_url`、`fish_species`、`title`；最多 3 張，超過顯示 `+N`；沒有照片顯示 placeholder；不連商品頁、不做 lightbox。
- 日期：30 天內顯示相對時間，超過顯示 `YYYY/MM/DD`。
- 桌面 3 欄、手機 1 欄；卡片高度自然，不強制等高。

### 3. 評價角色與交易房標題列

- 評價方向以 `reviews.reviewer_role` 判斷：
  - `reviewer_role = buyer`：買家給的評價；被評價者是釣客。個人資訊頁稱「買家給的評價」，也就是該使用者作為釣客的評價。
  - `reviewer_role = seller`：釣客給的評價；被評價者是買家。個人資訊頁稱「釣客給的評價」，也就是該使用者作為買家的評價。
- 個人資訊頁的角色 tabs 與 header chips 使用同一組文案；不要用單獨的「買家評價」或「釣客評價」以免方向不明。
- 交易房標題列：
  - 有訂單（`deal` 存在）時，顯示對方在該交易角色的評價：目前使用者是買家→對方是釣客→用買家給的評價；目前使用者是釣客→對方是買家→用釣客給的評價。
  - 純聊天房（沒有商品、沒有訂單）顯示對方的整體評價。
  - 角色評價數為 0 時顯示「尚無評價」，不要退回整體平均。
- 對話摘要（收件匣）的 `peer` 可維持整體評價；交易房開啟後以訂單的 peer 角色評價為準。

### 4. 商品管理

- 自己的個人資訊頁商品區標題列有「管理商品」；按下後變成「完成」，所有卡片進入管理模式。
- 管理模式下的卡片動作：
  - `ACTIVE`／`PARTIALLY_RESERVED`：下架。
  - `DELISTED`：重新上架、刪除（沒有未售尾數時只有刪除）。
  - `SOLD_OUT`：刪除。
- 「完成」離開管理模式；卡片留在原位，狀態徽章更新。
- 下架／刪除沿用現有上架紀錄的 `window.confirm` 文案與後端行為；重新上架不跳確認。
- 下架後卡片仍留在自己的頁面，顯示「已下架」；別人的頁面立即看不到。
- 刪除後卡片從自己的頁面移除。
- 不做上架中／已下架／已售出 tabs；用自己的頁面狀態徽章取代。
- 商品區不重複顯示「上架紀錄」按鈕；導覽列與抽屜仍保留上架紀錄入口。

### 5. 聊聊與交易房

- 「聊聊」只在別人的個人資訊出現；自己的頁面顯示「編輯個人資訊」。
- 未登入按聊聊 → 導到登入頁。
- 後端新增由個人資訊開啟交易房的端點，請求帶對方的 `seller_id`；目前使用者是買家，對方是釣客。
- 不能對自己開房。
- 已經有同一方向的交易房時沿用，不建立第二間。
- 對方有公開商品時：
  - 找或建立 `DRAFT` 訂單；購物車為空，顯示「選購」與停用的「發送交易」。
  - 如果已有進行中訂單，回傳該訂單；房間為唯讀，不建立新草稿。
- 對方沒有公開商品時：
  - 不建立訂單，回傳 `deal: null`；房間只聊天，不顯示浮動購物車。
  - 建立房間時留一則系統訊息「已開啟對話」；有商品的房間留「已進入交易洽談」。
- 純聊天房（沒有任何訂單）可以隨時刪除；有訂單時沿用現行交易房刪除規則（沒有 `CONFIRMED` 且目前訂單為 `CANCELLED`）。
- 房間方向固定：按聊聊的人＝買家、被看的人＝釣客。反向交易是另一間房；文件把「同一組人只有一間」改成「同一組買家與釣客只有一間（方向固定）」。
- 交易房標題列的電話沿用現行規則直接顯示；純聊天房也顯示。這是刻意選擇，spec 與 UI 文件要註明隱私 trade-off。
- 空房會出現在收件匣；純聊天房沒有訂單摘要。

### 6. 購物車（訂單草稿的浮動框）

- UI 可以把浮動框當成小型購物車，但文件與程式仍叫**訂單草稿**；「購物車」不是新的資料模型。
- 對方有商品、草稿為空：顯示「尚未加入商品」、按鈕「選購」、停用的「發送交易」。
- 草稿有商品：每個商品一列，顯示魚種、處理方式（若有）、剩餘尾數、價格；每列有「移除」與數量控制；按鈕「加購」與「發送交易」。
- 買家可以逐項移除與改尾數；釣客唯讀。
- 不做「清空全部」；要清空就逐項移除。
- 移除與改尾數不留系統訊息；加購（單筆或批次）仍留一則系統訊息。
- 最後一項被移除後，回到空草稿狀態；若對方仍有商品，顯示「選購」，不要隱藏浮動框。
- 對方完全沒有商品：不顯示浮動框，只顯示訊息流與輸入框。
- 發送交易在草稿為空時停用；有商品時可開協議面板。
- 進行中／已成交／已取消訂單的浮動框維持現行唯讀規則，不提供移除或改數量。

### 7. 設定頁與電話

- 設定頁欄位：
  - 頭像：上傳、預覽、移除；上傳沿用現有圖片上傳端點，儲存 `avatar_url`；沒有頭像顯示名字首字。
  - 暱稱：2–20 字，沿用現有驗證。
  - 電話：可編輯；格式 `09` 開頭共 10 碼；全站唯一。
  - 縣市：必填，使用現有縣市資料與「台」正規化。
  - 鄉鎮市區、詳細地址：選填，長度沿用現有欄位限制。
  - 儲存變更：一次送出所有變更；成功後更新本機會員資料、導覽列頭像與名字。
- 電話修改不要求目前密碼，也不強制重新登入；token 綁 user id，修改後仍有效。下一次登入使用新電話。
- 電話重複回 409，格式錯誤回 400；設定頁顯示欄位錯誤，不整頁失敗。
- 銀行欄位這次不做。
- 公開個人資訊只使用 `display_name`、`avatar_url`、`region`、`completed_deals`、`is_verified` 與角色評分；電話與地址只在設定頁與自己的 session 資料中出現。
- 自己的頭像上傳後，舊的 `localStorage` 頭像不再是來源；後端 `avatar_url` 為唯一真實來源。既有本機頭像可忽略，不做自動遷移。

### 8. 資料模型

- `users` 新增 `avatar_url`（string，可為空）。
- `users.username`（電話）仍為唯一鍵，但允許透過設定頁更新；更新不影響 user id、token、訂單或對話。
- `users.rating_score`／`review_count` 保留為整體評分；角色評分不落庫，讀取時用 reviews 計算：
  - 作為釣客：`reviewer_role = buyer` 的評價。
  - 作為買家：`reviewer_role = seller` 的評價。
- `reviews` 不新增欄位；方向用既有 `reviewer_role`。
- 評價卡商品照片不落庫；從 `reviews.deal_id` 對到 `deals.items` 快照的 `photo_url`、`fish_species`、`title`。商品刪除後照片檔保留，因此舊評價仍可顯示。
- `conversations` 維持 `assistant`／`deal` 兩種；不新增直接對話型別。無商品的交易房仍是 `deal` 房，但沒有任何 `deal` 資料。
- 交易房唯一鍵仍是 `type + buyer_id + seller_id`，因此方向固定；反向交易是另一間房。
- 訂單項目與購物車資料結構不變；逐項移除與改數量使用既有 `deals.items` 操作。
- 商品管理沿用 `products.delisted_at`、`listed_at` 與現有狀態推導，不新增欄位。

### 9. API 契約

**公開個人資訊**

`GET /api/users/:id`（公開）

```json
{
  "id": 1,
  "display_name": "陳阿海",
  "avatar_url": "/uploads/avatar.jpg",
  "region": "新北市",
  "is_verified": true,
  "completed_deals": 18,
  "rating": {
    "overall": { "score": 4.8, "count": 20 },
    "as_seller": { "score": 4.9, "count": 18 },
    "as_buyer": { "score": 4.5, "count": 2 }
  }
}
```

- 不回傳 `username`、`password`、地址、銀行欄位、`seller_terms_accepted_at`。
- 找不到回 404 `USER_NOT_FOUND`。

**公開評價**

`GET /api/reviews?user_id=&role=&sort=&rating=&offset=&limit=`

- `role=seller`：該使用者作為釣客的評價 → 篩 `reviewer_role = buyer`。
- `role=buyer`：該使用者作為買家的評價 → 篩 `reviewer_role = seller`。
- 省略 `role`：整體評價，保留舊行為。
- `sort`：`newest`（預設）／`highest`／`lowest`。
- `rating`：1–5，選填；只影響列表，不影響 summary。
- `offset` 預設 0；`limit` 預設 20、最大 50；個人資訊頁傳 6。
- `summary` 依 role 計算全部評價；`total` 是目前 role + rating 篩選後的筆數；`has_more = offset + reviews.length < total`。

```json
{
  "user_id": 1,
  "role": "seller",
  "summary": {
    "score": 4.9,
    "count": 18,
    "distribution": { "5": 15, "4": 2, "3": 1, "2": 0, "1": 0 }
  },
  "total": 18,
  "reviews": [
    {
      "id": "rev_...",
      "rating": 5,
      "tags": ["魚貨新鮮", "準時守約"],
      "comment": "魚很新鮮，面交準時。",
      "created_at": "2026-11-01T10:00:00.000Z",
      "reviewer_id": 2,
      "reviewer_name": "小魚買家",
      "reviewer_avatar_url": "/uploads/buyer.jpg",
      "reviewer_role": "buyer",
      "products": [
        { "title": "紅魽（3尾 / 放血冰鎮）", "fish_species": "紅魽", "photo_url": "/uploads/a.jpg" }
      ]
    }
  ],
  "has_more": true
}
```

- 評價者只回名字與頭像，不回電話、地址。
- `products` 最多回 3 筆；超過時另回 `product_count`。沒有訂單或商品時回空陣列。
- 評價卡照片不新增上傳端點。

**更新個人檔案**

`PUT /api/users/profile`（登入）

```json
{
  "display_name": "陳阿海",
  "phone": "0912345678",
  "avatar_url": "/uploads/avatar.jpg",
  "city": "新北市",
  "district": "瑞芳區",
  "address_line": "鼻頭路 1 號"
}
```

- `phone` 對應 `username`；格式 `^09\d{8}$`，重複回 409 `PHONE_TAKEN`。
- `avatar_url` 只接受 `/uploads/...` 或空字串；空字串代表移除。
- 不要求目前密碼；不重新簽 token。
- 回應自己的 `publicUser`，包含 `avatar_url` 與 `username`。

**由個人資訊開交易房**

`POST /api/deals/initiate-room`（登入）

```json
{ "seller_id": 1 }
```

回應：

```json
{
  "conversation": { "id": "conv_...", "type": "deal", "peer": { "...": "..." } },
  "deal": { "id": "deal_...", "deal_status": "DRAFT", "items": [] },
  "has_products": true
}
```

- 目前使用者是買家，`seller_id` 是釣客；不能等於自己（400 `OWN_PROFILE`）。
- 對方有公開商品：找或建立草稿，`has_products: true`。
- 對方沒有公開商品：不建立 `deal`，`deal: null`、`has_products: false`。
- 既有同方向房間沿用；已有進行中訂單時回傳該訂單，不建立新草稿。
- 新房間的系統訊息：有商品「已進入交易洽談」；無商品「已開啟對話」。

**交易房 peer 評價**

- `GET /api/deals/:id` 的 `peer` 依目前使用者的交易角色回傳角色評價：
  - 目前使用者是買家：`peer` 是釣客，`rating_score`／`review_count` 用買家給的評價。
  - 目前使用者是釣客：`peer` 是買家，用釣客給的評價。
- 對話摘要的 `peer` 可維持整體評價；交易房開啟後以訂單的 peer 為準。
- 純聊天房沒有訂單，標題列使用對話摘要的整體評價。

**購物車**

- 沿用既有端點：
  - `POST /api/deals/items`、`POST /api/deals/items/batch`：加購，留一則系統訊息。
  - `PATCH /api/deals/items/:itemId`：改尾數，不留訊息。
  - `DELETE /api/deals/items/:itemId`：移除，不留訊息。
- `DELETE /api/deals/items`（清空）保留給舊資料／內部使用，UI 不提供。
- 權限：只有買家、只有 `DRAFT` 可以改；釣客唯讀。

**刪除房間**

- 純聊天房（沒有任何 `deals`）任何時候可刪。
- 有訂單時沿用現行規則：沒有 `CONFIRMED`，且目前訂單為 `CANCELLED`（或全部取消）才可刪。
- 刪除純聊天房時移除訊息；不影響任何訂單或商品。

### 10. 隱私與權限

- 公開個人資訊是公開讀取，不需登入；聊聊與設定需登入。
- 公開頁只回公開欄位白名單；不得直接重用含電話與地址的 `publicUser`。
- 評價者只回名字、頭像與評價內容；不回電話、地址。
- 評價商品照片是刻意公開的交易快照；商品名稱與照片可能顯示使用者買過什麼。
- 交易房標題列仍顯示電話；純聊天房讓任何登入者按聊聊就能看到對方電話，這是刻意接受的风险，文件要註明。
- 電話修改不要求目前密碼是刻意選擇；任何持有登入 token 的人都能改登入電話。文件要註明風險。
- 自己的頁面可看全部商品；別人的頁面只回公開商品。

### 11. 種子資料

- 目前 seed 的 `reviews` 是 0 筆，但 `users.rating_score`／`review_count` 有舊數字。新的公開頁會以 reviews 重算，因此會顯示 0 則。
- 補 8–10 筆種子評價與對應的 `CONFIRMED` 訂單／訂單項目，讓：
  - 使用者 1（陳阿海）有買家給的評價（作為釣客），也有少量釣客給的評價（作為買家）。
  - 使用者 2（小魚買家）有釣客給的評價（作為買家），也有少量買家給的評價（作為釣客）。
  - 評價星的分布涵蓋 3–5 星，標籤與評語有變化。
  - 訂單項目有 `photo_url`，讓評價卡有商品照片。
- `users.rating_score`／`review_count` 用評價重算後同步，不沿用舊數字。
- `db.json` 是執行時資料；種子變更後需刪除 `backend/db.json` 重建，或提供一次性遷移。沒有遷移工具時，文件要寫明重置步驟。

## Testing Decisions

好的測試只驗外部行為：API 的 request／response、權限、隱私欄位、狀態轉移、畫面渲染輸出與可存取性；不要測私有函式、DOM 實作細節或固定字串以外的內部結構。

主要 seam：

1. **後端 HTTP API**（最高 seam，優先使用既有 `node:test` 整合測試與暫存資料庫）：
   - 公開個人資訊：白名單欄位、404、角色評分、隱私欄位不存在。
   - 評價：role 篩選、排序、rating 篩選、offset／limit、distribution、has_more、商品照片、reviewer 頭像、無電話。
   - 電話修改：格式、重複、成功後 token 仍有效、登入使用新電話。
   - 頭像：`avatar_url` 儲存、移除、公開頁顯示。
   - 開房：自己不可開、對方有商品建空草稿、對方無商品 `deal: null`、既有房沿用、進行中訂單不建新草稿、純聊天房可刪。
   - 購物車：加購留訊息、移除與改數量不留訊息、釣客不可改、空車不可送協議。
   - 商品管理：自己的頁面回全部、別人的頁面只回公開、下架／重新上架／刪除沿用既有規則。
2. **前端純渲染模組**（既有 ESM／VM 測試模式）：
   - 個人資訊標題列與評分 chips 的排序、空狀態、自己／別人動作。
   - 評價 tabs、摘要、分布、排序、星等篩選、卡片、商品照片 `+N`、載入更多。
   - 商品卡管理模式：狀態對應的按鈕、完成切換、狀態徽章。
   - 購物車空車／有商品／無商品三種狀態、移除與數量控制、發送交易停用。
   - 設定頁表單驗證、電話錯誤、頭像 fallback、儲存成功後的 nav 更新。
   - 交易房標題列角色評價與純聊天整體評價。
3. **頁面契約測試**（既有字串／檔案存在性測試）：
   - 新頁面有 header／footer placeholder、正確載入共用 CSS／JS、導覽連結、沒有舊的 `product-detail` 連結。
   - 商品卡「釣客資訊」是連到個人資訊的連結，不是沒有行為的按鈕。
   - 導覽列「我的」有個人資訊、設定、交易紀錄、上架紀錄。

## Out of Scope

- 新增「直接對話」房間型別；這次沿用交易房，無商品時不建訂單。
- 評價者上傳照片、有幫助投票、檢舉、Local Guide 徽章、商家回覆、撰寫評價 CTA。
- 評價照片 lightbox 或連到商品頁。
- 商品詳情頁。
- 別人的個人資訊顯示已下架或已售出商品。
- 銀行欄位、提領功能。
- 電話修改的 SMS 驗證、目前密碼驗證、強制重新登入。
- 同一組人雙向交易共用一間房；這次維持方向性房間。
- 即時 WebSocket；沿用 3 秒輪詢。
- 實作 tickets；這次只交付文件。
