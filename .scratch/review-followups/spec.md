# Review 後續修正：交易摘要、訊息去重與單一來源收斂

**Status:** resolved

**Source:** `.scratch/review-followups/spec.md`，源自 2026-10-27 對 `a5ef9fe..c80aa7a`（15 筆提交）的 Standards／Spec 雙軸審查。

## Problem Statement

使用者在交易房完成或取消交易後，回到收件匣仍看到「洽談中」；點進交易房，訂單摘要退成「尚無訂單」。原因是畫面只讀「進行中訂單」，沒有在看「最新一筆訂單」。

使用者在助手房收到 AI 連續多則回覆時，3 秒輪詢可能把同一則訊息再顯示一次；訊息列表會出現重複內容，且「已讀到第幾則」的游標可能落後。

維護者面對同一條規則散落在多處：取消與逾時各寫一份狀態轉移、台斤換算與一位小數格式各有多份、商品標題前後端各有一套、訂單狀態字串在前端兩處列舉。結果是改一處、漏一處，且模組名稱難以分辨誰是狀態常數、誰是狀態轉移。API 文件也落後於實作，新增的前端函式查不到；部分檔案已貼近 200 行上限。原 ticket 要求的人工視覺驗收（demo API 搬移、死 CSS 移除）尚未執行。

## Solution

做一輪行為修正與收斂，不新增功能：

- 房間摘要一律採「進行中訂單，否則最新一筆訂單」，收件匣與訂單面板共用同一條規則。
- 訊息串接改成冪等：以訊息序號去重，AI 回覆與輪詢都走同一條路徑。
- 把重複規則收成單一來源：取消／逾時共用一個取消核心、前端狀態文案與卡片對應共用一個模組、台斤換算與一位小數各只有一份、商品標題只由後端產生、魚種名稱只由魚種清單提供。
- 補齊 API 文件、完成 ticket 要求的人工視覺驗收，並記錄兩個已上線但無 ticket 的合理修正。
- 維持每個程式碼檔案不超過 200 行。

使用者看到的結果：交易結束後摘要正確、訊息不重複、行情與商品文案一致；維護者看到的結果：同一規則只有一處、文件可查、檔案不再貼線。

## User Stories

1. 作為買家，我想在成交後於收件匣看到「已成交」，而不是「洽談中」，以便確認交易狀態。
2. 作為釣客，我想在訂單取消後於收件匣看到「已取消」，以便知道對方已結束交易。
3. 作為使用者，我想在協議逾時後於收件匣看到「已逾時」，以便區分逾時與主動取消。
4. 作為使用者，我想在房間沒有任何訂單時看到「洽談中」，以便知道對話已開始但尚未建立訂單。
5. 作為使用者，我想在收件匣看到最新訂單的品項數、尾數與金額，以便不必點進房間就能掌握交易。
6. 作為使用者，我想讓收件匣摘要在 3 秒內跟上對方的操作，以便看到即時的訂單變化。
7. 作為買家，我想在訂單面板看到已結束訂單的摘要，而不是「尚無訂單」，以便回顧剛才的交易。
8. 作為使用者，我想在房間有多筆歷史訂單時看到最新一筆，以便摘要不會停在舊交易。
9. 作為使用者，我想在同時有進行中與歷史訂單時優先看到進行中訂單，以便摘要反映目前正在談的交易。
10. 作為使用者，我想在已成交或已取消的訂單面板看到狀態與金額，但不再看到改量、加購、同意或取消操作，以便避免誤操作。
11. 作為使用者，我想在 AI 一次回覆多則訊息時只看到每則一次，以便閱讀不混亂。
12. 作為使用者，我想在輪詢與 AI 回覆同時發生時不看到重複訊息，以便訊息順序穩定。
13. 作為使用者，我想讓「已讀到第幾則」的游標正確前進，以便重新整理後不會重抓舊訊息。
14. 作為使用者，我想在同意販賣法規後只看到新的提問，先前的對話紀錄仍正確清除，以便畫面乾淨。
15. 作為使用者，我想讓手動取消與逾時取消得到一致的結果（狀態、保留釋放、卡片狀態、系統訊息），以便規則可預期。
16. 作為使用者，我想在重複讀取對話或訂單時不會重複收到取消通知，以便系統訊息不洗版。
17. 作為釣客，我想讓行情卡的台斤換算與草稿的自動計算使用同一個換算值，以便估價一致。
18. 作為釣客，我想讓每台斤與整批售價的換算結果在儲存前後一致，以便金額不會前後不同。
19. 作為使用者，我想讓商品卡標題與後端回傳的標題完全一致，以便列表、詳情與對話中的名稱相同。
20. 作為使用者，我想在商品缺少標題時看到不誤導的通用文案，而不是前端自行拼出的格式。
21. 作為使用者，我想讓訂單狀態文案與協議卡狀態永遠對應，以便同一筆交易在訊息卡片與訂單面板顯示一致。
22. 作為維護者，我想在新增一個訂單狀態時只改一處，以便不會漏掉文案或卡片對應。
23. 作為維護者，我想讓「狀態常數」與「狀態轉移」的模組名稱可以分辨，以便快速找到正確檔案。
24. 作為維護者，我想讓使用者取消與逾時取消共用同一個取消核心，以便修正一次就同時生效。
25. 作為維護者，我想讓魚種的顯示名稱與別名只由魚種清單提供，以便行情對照不再重複維護名稱。
26. 作為維護者，我想在行情對照端點維持代碼、分類與養殖旗標不變，以便行情查詢不受名稱整理影響。
27. 作為維護者，我想讓 0.6 公斤／台斤只以一個常數存在，以便單位換算不會漂移。
28. 作為維護者，我想讓一位小數的格式化只有一份，以便行情數字顯示一致。
29. 作為維護者，我想讓商品建立與定價驗證從路由抽出，以便每個檔案都遠離 200 行上限。
30. 作為維護者，我想在 API 文件查到前端新增的商品建立函式與商品清單參數，以便串接時不用讀原始碼。
31. 作為維護者，我想讓 demo 種子資料自帶合法縣市，而不是在每次啟動時隨機補值，以便每次啟動結果可重現。
32. 作為產品負責人，我想完成首頁、商品列表、登入頁與對話上架流程的人工視覺驗收，以便確認先前的搬移與 CSS 移除沒有破壞畫面。
33. 作為產品負責人，我想讓兩個已上線但無 ticket 的修正留下紀錄，以便範圍外變更有跡可循。
34. 作為維護者，我想在修正後跑完整測試並確認所有程式碼檔案不超過 200 行，以便這輪收斂不會引入新債。

## Implementation Decisions

### 房間摘要

- 前端只保留一條摘要取值規則：優先使用進行中訂單，沒有才用最新一筆訂單，兩者都沒有才視為無摘要。
- 收件匣與訂單面板都呼叫同一個摘要規則，不各自讀不同欄位。
- 助手房仍顯示「AI 對話」；交易房沒有摘要時顯示「洽談中」；訂單面板沒有摘要時顯示「尚無訂單」。
- 已結束訂單只顯示狀態、品項數、尾數與金額，不提供任何操作方法。

### 訊息串接

- 前端共用狀態層新增兩個動作：以完整清單取代訊息，以及追加訊息。
- 追加時以訊息序號去重；序號缺漏時退回以訊息識別碼去重。重複訊息不改變順序，也不重複計入未讀。
- 「已讀到第幾則」取清單中最大序號，而不是最後一筆陣列的序號。
- AI 回覆流程與 3 秒輪詢都只透過這兩個動作改動訊息；輪詢不再自行串接陣列或更新游標。
- 「清除歷史後只留新訊息」走取代路徑，不走去重路徑。

### 訂單生命週期

- 後端抽出一個取消核心，接受：操作者（使用者或系統）、取消原因代碼、要同步的卡片狀態、要留下的系統訊息。
- 使用者主動取消與逾時掃描都呼叫這個核心；兩者的差異只剩參數，不再各寫一份欄位更新。
- 逾時掃描仍以「狀態＋到期時間」判斷，狀態一旦離開待回覆／協商中就不再重複處理，因此重複掃描不會重複寫入系統訊息。
- 取消原因代碼與既有系統訊息文字維持不變，避免使用者看到的文案改變。
- 後端狀態常數模組只放狀態清單與「進行中」判定；狀態轉移模組改名為可與常數區分的名稱，所有引用同步更新。

### 前端狀態來源

- 前端共用狀態模組同時擁有：訂單狀態文案、卡片狀態文案、狀態提示、訂單狀態到卡片狀態的對應、可操作狀態清單、逾時原因清單。
- demo 層只轉出共用模組的函式，不再自行列舉狀態字串。
- 新增狀態時只需改共用模組；測試需鎖定每個訂單狀態都有文案與卡片對應。

### 單位、數值與標題

- 台斤換算值在後端與前端各只有一個常數（兩個 runtime 不共用檔案），所有換算都引用它，不得再出現 0.6 字面值。
- 一位小數四捨五入由前端共用格式提供，行情卡改用共用版本；後端沿用既有的四捨五入模組。
- 商品標題只由後端產生並隨商品回應回傳；前端不再自行組合魚種、重量、尾數與處理方式。標題缺漏時顯示通用文案，不拼出可能與後端不同的格式。

### 魚種與行情對照

- 行情對照端點的顯示名稱與別名一律由魚種清單帶出；代碼、分類與養殖旗標維持不變。
- 接受顯示名稱變更（例如七星鱸改為海鱸、鯖魚改為白腹鯖、小卷改為澎湖小卷、巴攏改為竹筴魚），不還原舊字串；此變更需在 API 文件與原 ticket 註明。
- 測試鎖定：每個行情代碼的顯示名稱等於魚種清單名稱、別名等於魚種清單別名，且代碼集合與分類不變。

### 檔案結構與命名

- 商品建立流程中的定價驗證與自動計算抽成獨立模組，路由只負責 HTTP 與組裝回應；抽出後所有程式碼檔案維持 200 行以下。
- 後端訂單狀態轉移與狀態常數改名後，所有引用一併更新，不留舊名別名。
- 卡片同步模組的匯出語句獨立成行，維持既有排版慣例。

### 種子資料

- 種子資料中沒有縣市的兩個使用者補上固定且合法的縣市。
- 移除伺服器啟動時「隨機補縣市」的執行期邏輯與其測試。
- 改為種子資料測試：每位種子使用者都有縣市，且縣市在合法清單內。

### 文件

- API 文件補上商品建立函式與商品清單的查詢參數，並註明商品標題由後端保證。
- API 文件註明行情對照的名稱來源與已接受的顯示變更。
- 兩個已上線但無 ticket 的修正（登出清除本機 token、登入頁法規強調）保留，於本 spec 與 remediation README 記錄為已接受的範圍外修正。

### 人工驗收

- 依原 ticket 執行：首頁、商品列表、商品詳情、登入頁的外觀與互動比對；對話上架、商品列表與行情卡的人工檢查。
- 驗收結果（含日期、瀏覽器、帳號與觀察）寫回對應 ticket 的 Comments。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、畫面渲染出的 HTML、共用狀態層的公開動作、行情對照端點的輸出。測試不驗私有函式名稱、不驗內部呼叫次數，也不為了測試而把模組拆得更細。

沿用五個既有斷層，不新增斷層：

1. **後端 HTTP（最高層）**：以既有測試伺服器啟動後打真實端點。涵蓋對話清單的訂單摘要、訂單明細、同意／退回／取消與逾時掃描。既有前例：逾時掃描測試、訂單生命週期測試、對話摘要測試。
2. **前端共用狀態**：直接使用共用狀態層的公開動作與狀態。涵蓋追加去重、游標前進、清單取代。既有前例：卡片同步與房間狀態測試。
3. **前端視圖渲染**：以狀態注入後取得 HTML 字串。涵蓋收件匣已成交／已取消／已逾時／無訂單，以及訂單面板的已結束摘要。既有前例：收件匣測試、訂單面板測試。
4. **前端共用格式全域**：透過全域格式物件驗證一位小數與行情文字。既有前例：格式測試。
5. **魚種對照**：直接呼叫對照模組並打行情代碼端點。既有前例：行情對照測試。

需新增或擴充的案例：

- 進行中訂單存在時，收件匣與訂單面板都優先顯示它。
- 只有最新訂單、且已成交或已取消時，兩處都顯示該訂單的狀態與金額。
- 兩者都沒有時，收件匣顯示「洽談中」、訂單面板顯示「尚無訂單」。
- 追加重複序號的訊息不會增加長度，游標停在最大序號。
- 追加以外的訊息順序穩定；取代清單後只保留新訊息。
- 使用者取消與逾時取消產生相同的狀態、保留釋放與卡片狀態，但系統訊息與操作者不同。
- 重複掃描不重複寫入系統訊息。
- 一位小數格式對整數、負值與字串輸入的行為與既有格式一致。
- 行情卡使用共用的一位小數格式。
- 每個行情代碼的名稱與別名等於魚種清單，代碼、分類與養殖旗標不變。
- 種子資料的每位使用者都有合法縣市。

完整測試以既有 `npm test` 執行（Node 內建測試 runner，涵蓋後端與前端測試）。

## Out of Scope

- 不改動對外 API 契約；唯一例外是行情對照端點的顯示名稱與別名，這是已接受並需記錄的變更。
- 不重新設計畫面、導覽或視覺風格；只做原 ticket 要求的人工比對。
- 不引入新框架、建置工具、TypeScript 或新的執行期依賴。
- 不建立資料庫遷移框架；種子補值以修改種子資料解決。
- 不新增自動視覺回歸或瀏覽器自動化測試。
- 不處理上輪審查未列出的新功能或新重構。
- 不回退兩個已上線、無 ticket 的合理修正。
