# Review 修正：AI 功能批次（30 commits）的 Standards／Spec 後續

**Status:** ready-for-agent

**Source:** 2026-11-22 對 `origin/master..HEAD`（30 commits，涵蓋 llm-assistant、publish-dedup、local-conditions、cwa-weather、llm-listing）的 Standards／Spec 雙軸 review。Standards 軸：0 硬違規、5 判斷性 smell。Spec 軸：2 偏差（皆在 llm-listing）。

## Problem Statement

釣客在助手房用模型驅動上架時，有兩個承諾沒有被程式真正保證：

- 處理方式「兩次回問後才提議縮短版」只寫在模型提示詞，後端不追蹤回問次數、也不強制；模型可能在第一次就提議縮短版，或一直不提議。
- 修正紀錄（corrections）的欄位驗證允許了 spec 未授權的欄位（尾數、整批售價、每台斤售價），與 spec「修正只限魚種與處理方式」的契約不一致；目前靠套用階段靜默丟棄，埋下未來誤用風險。

此外，review 也標出幾處重複樣板：`conditions/` 四個資料源各自重複 fetcher 注入；intent 常數前後端各一份；listing 流程重複 deadline 剩餘時間算式。

## Solution

- 把「可修正欄位」與「草稿變更欄位」分開：修正紀錄只接受魚種與處理方式，尾數與售價不得進入修正紀錄。
- 為「兩次回問」加入後端狀態追蹤與強制：conversation context 新增回問計數；模型輸出新增「是否回問處理方式」的訊號；提議縮短版只在回問計數達兩次後接受，否則降級成回問。回問計數在處理方式寫入有效值後歸零。
- fetcher 注入樣板收斂成單一 factory，各資料源仍保留獨立注入點，測試斷層不變。
- 文件化前後端 intent 常數的對應，避免改動時漏同步。
- 抽出 deadline 剩餘時間算式，集中一處。

## User Stories

1. 作為釣客，我想處理方式超過 20 字或只有數字／單位時被回問，以便我知道要縮短。
2. 作為釣客，我想前兩次處理方式無效時只被回問、不被提議縮短版，以便模型不會太早替我改寫。
3. 作為釣客，我想兩次回問仍無效時看到助手提議的 20 字內版本，以便我不會卡住。
4. 作為釣客，我想只有在回答「好」之後才套用提議版本，以便我不被自動改寫。
5. 作為釣客，我想魚種與處理方式的錯字修正仍然可用，以便商品名稱正確。
6. 作為釣客，我想尾數與售價不會被當成「錯字修正」，以便數字欄位只由我這一則訊息決定。
7. 作為維護者，我想修正紀錄只接受魚種與處理方式欄位，以便驗證契約與 spec 一致。
8. 作為維護者，我想處理方式回問次數由後端追蹤與強制，以便「兩次」不依賴模型自發遵守。
9. 作為維護者，我想 fetcher 注入樣板收斂成單一 factory，以便新增資料源不用再複製一份。
10. 作為維護者，我想前後端 intent 常數的對應有文件標註，以便改動時知道要同步哪裡。
11. 作為維護者，我想 deadline 剩餘時間算式集中一處，以便減少重複。
12. 作為維護者，我想所有程式檔案維持在 200 行以內，以便符合專案規範。
13. 作為維護者，我想更新 GLOSSARY、ADR 與相關 spec 反映契約變更，以便文件與程式一致。

## Implementation Decisions

### 修正紀錄欄位

- 「草稿變更欄位」維持魚種、尾數、處理方式、整批售價、每台斤售價；「可修正欄位」只含魚種與處理方式，兩者分開定義。
- 修正紀錄的欄位驗證在解析階段就拒絕欄位不在「可修正欄位」的項目，而不是放到套用階段才靜默丟棄。

### 處理方式兩次回問

- conversation context 新增回問計數欄位（整數、預設 0），屬草稿層級、與既有草稿欄位一致，不需資料遷移。
- 模型輸出新增「是否回問處理方式」訊號（布林），供後端遞增回問計數；此訊號與既有的 next_action、condition_proposal 一起驗證。
- 提議縮短版只在回問計數 ≥ 2 時接受；未達兩次時，後端丟棄該提議並降級成回問，不切換基本模式。
- 處理方式寫入有效值（含錯字修正或經同意的縮短）時，回問計數歸零。
- 提示詞同步：模型在回問處理方式時要送出該訊號；提議縮短版前要確認回問計數已達兩次。

### fetcher 注入 dedup

- 抽出共用 factory 產生「可注入 fetcher 插槽」（set / reset / current 三件組），供各資料源模組使用。
- 每個資料源仍保留自己的獨立插槽與既有 `setFetcher`／`resetFetcher` 匯出，測試注入點不變。
- 純重構，不改變任何上游請求行為或逾時語意。

### intent 常數對應

- 前後端各別維護（受前後端模組系統隔離限制），在兩處加互相指向的註記，說明對應關係與「改一邊要同步另一邊」。

### deadline 剩餘時間

- 抽出單一「剩餘毫秒」helper（下限 1ms），取代 listing 流程中重複的算式；查詢預算的 3000ms 上限以該 helper 為底再取 min。

### 200 行

- 目前三個檔案恰為 200 行、未超標；不為了湊行數強拆。僅在本次觸及的檔案因新增邏輯而逼近上限時，才依職責拆分。

### 文件

- 更新 llm-listing spec 的修正契約與 conversation context 欄位；更新資料模型 spec 的 context 欄位；必要時更新 GLOSSARY。
- 完成註記回寫到對應 tickets。

## Testing Decisions

好的測試只驗外部行為：HTTP 狀態與 JSON、回覆文字、context 欄位。不驗私有函式名稱、不驗內部呼叫堆疊，也不為了測試把模組拆得更細。

沿用既有斷層，不新增 seam：

1. **後端 HTTP（最高層）**：沿用既有測試伺服器、登入 Token、對話／訊息 helper 與 provider 注入點（假模型回覆）。既有前例：處理方式測試、AI 回覆 helper、CWA 測試 helper。
2. 前端對話流程、草稿卡渲染、E2E（offline）本批皆無行為變化，不新增測試。

必測：

- 修正紀錄只接受魚種與處理方式：欄位為尾數或售價的修正項目使整輪被拒。
- 回問計數：回問訊號遞增；計數 < 2 時提議被拒／降級成回問；計數 = 2 時提議被接受；有效處理方式寫入後計數歸零。
- fetcher dedup 後，既有 CWA 預報／觀測／潮汐／Open-Meteo 測試全綠（不新增、不改斷層）。
- deadline helper 後，既有 listing 測試全綠。
- 完成後 `npm test` 全綠，所有程式檔案 ≤ 200 行。

## Out of Scope

- 前後端 intent 常數完全單一來源（受前後端模組系統隔離，建置層方案另議）。
- Repeated Switches 改 lookup map 或多型（低優先）。
- Data Clumps 打包（低優先）。
- 三個 200 行檔案的強制拆分（未超標）。
- 別名搜尋、錯字模糊搜尋等其他功能。
- 不改變任何既有外部行為；本批為契約修正與純重構。

## Further Notes

- 回問次數機制會改變模型輸出 schema，需同步更新提示詞與輸出解析驗證，避免「訊息說回問、後端沒計到」。
- 三個 200 行檔案是風險旗標而非違規；後續任一新增都會踩線，宜在真正需要時拆分。
- 處理方式錯字仍無官方字典可驗證，編輯距離上限與釣客可改回仍是主要防線；本批不改變這項殘餘風險。
