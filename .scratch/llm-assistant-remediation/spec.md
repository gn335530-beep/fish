# Review 修正：助手房 LLM Beta 的隱私、逾時與意圖一致性

**Status:** ready-for-agent

**Source:** 2026-11-14 對 `20985e6..HEAD`（LLM assistant tickets 01–08）的 Standards／Spec 雙軸 review。原始功能 spec 位於 `.scratch/llm-assistant/spec.md`，行為契約以 `docs/adr/0011-hybrid-llm-assistant.md`、`GLOSSARY.md` 與 `docs/spec/` 為準。

## Problem Statement

助手房 LLM Beta 已經可以理解自然語言、回答一般知識、查網路資料與推薦商品，但 review 發現幾個會直接影響使用者的問題：

- 個資遮蔽同時過度與不足。一般句子只要含有「路」或「弄」就可能被換成 `[已遮蔽]`，但 `+886` 手機、含括號區碼的市話與含「里／鄰」的地址反而原樣送到 Gemini 與 Tavily。
- 重試沒有錨定原本的訊息。使用者在按重試前又送了一則新訊息時，模型會把新訊息當成最後一輪，回覆卻被寫成舊訊息的重試結果。
- 行情工具沒有遵守回覆逾時。一般回覆承諾 8 秒，但行情上游仍可能跑到 15 秒，使用者會一直看到「小幫手正在輸入…」。
- 商品推薦加上查詢範圍後綴後，可能在最後一刻超過 500 字上限，整則回覆被靜默丟棄並 fallback。
- 來源與 intent 的語意不一致：模型在 `CHAT` 中用了網路搜尋時，後端會把 `sources` 清空；但原始 spec 又說 `CHAT` 有來源時要顯示來源卡。
- 前端會用自製的關鍵字規則否決後端回傳的 `PRODUCT_RECOMMEND`，即使後端已經找到符合的商品。
- 設定與文件漂移：歷史訊息與工具次數有未文件化的隱藏上限，與 ADR-0011 的「最近 10 則、每輪最多 2 次」不一致；領域文件也漏了 `sources` 卡片。

另外，這次變更留下了重複的錯誤建構子、兩份 slots 驗證、重複的 intent 分支與過度膨脹的 AI service，讓後續修正容易改一處漏一處。

## Solution

讓助手房的行為回到單一、可預期的契約：

- 只遮蔽真正的個資格式，不再誤傷一般文字；電話、Email、身分證與地址在送往外部服務前一致替換成 `[已遮蔽]`。
- 重試永遠針對同一個 `message_id`，模型只看得到含該訊息在內的歷史；不會回答到後來才送出的訊息。
- 每個 AI 回覆都受同一個請求期限約束：一般 8 秒、含網路搜尋 15 秒；行情工具也共用這個期限，逾時就靜默 fallback。
- 500 字上限以最後送出的文字為準；查詢範圍後綴若會超限就省略，不再讓整則回覆失敗。
- `WEB` 代表「這一輪用了網路資料」：只要 `web_search` 成功取得來源，回覆就升級為 `WEB` 並附上最多 3 個來源；`CHAT` 永遠是不帶來源的一般知識回答。
- 後端回傳的 intent 是主要依據；只有在平台動作（`SELL`、`MARKET`、`CANCEL`、`EDIT`）與上架流程進行中時，才由規則引擎優先。`PRODUCT_RECOMMEND` 不再被前端的關鍵字規則否決。
- 行情工具提供兩種視圖：模型只看到平均價、交易日期與必要識別資訊；行情卡仍取得完整歷史，維持既有的 7／30 個交易日走勢。
- 設定、文件與程式一致：歷史固定 10 則、每輪最多 2 次工具呼叫；領域文件補上 `sources` 卡片；README 只列出真正支援的環境變數。
- 順手收掉重複程式碼與命名問題，讓每個檔案維持在 200 行以內，且同樣的行為只有一份實作。

## User Stories

1. 身為使用者，我希望電話、Email、身分證字號與地址在送到 Gemini 或 Tavily 前被替換成 `[已遮蔽]`，以便我的個資不會外流。
2. 身為使用者，我希望含「路」或「弄」的一般句子（例如「網路上的天氣」「弄一桌好菜」）保持原樣，以便助手不會回覆被過度遮蔽的內容。
3. 身為使用者，我希望 `+886912345678`、`(02)12345678` 這類電話格式也被遮蔽，以便常見的台灣電話寫法都受到保護。
4. 身為使用者，我希望包含「里」「鄰」的完整地址也被遮蔽，以便地址不會因為格式不同而漏掉。
5. 身為使用者，我希望在按重試前又送出新訊息時，助手仍回答我當初要重試的那則訊息，以便回覆不會張冠李戴。
6. 身為使用者，我希望重試不會重複寫入我的訊息，以便對話維持乾淨。
7. 身為買家，我希望一則接近 500 字的商品推薦仍能完整送出，以便我不會因為查詢範圍後綴而失去整則回覆。
8. 身為使用者，我希望查詢範圍後綴只在不會超過 500 字時附加，以便長回覆仍能安全送出。
9. 身為使用者，我希望一般助手回覆在 8 秒內完成或 fallback，以便我不用一直等待。
10. 身為使用者，我希望含網路搜尋的回覆最多等 15 秒，以便有足夠時間取得即時資料。
11. 身為使用者，我希望行情查詢也遵守同一個期限，以便市場上游變慢時不會拖垮整個助手房。
12. 身為使用者，我希望網路回答下方最多顯示 3 個可點擊的資料來源，以便我自行查證。
13. 身為使用者，我希望一般知識回答不顯示資料來源，以便 `CHAT` 與 `WEB` 的差別清楚。
14. 身為使用者，我希望模型在 `CHAT` 中使用了網路資料時，該回覆被當成網路回答並顯示來源，以便來源與實際使用的資料一致。
15. 身為使用者，我希望平台行情、商品價格與庫存數字仍受嚴格防護，以便模型不會編造交易數字。
16. 身為買家，我希望說「有沒有澎湖的魚」時看到後端找到的商品推薦與商品卡，以便我不會只得到規則引擎的泛用引導。
17. 身為買家，我希望商品卡只由工具結果產生，以便模型不能自行捏造商品或價格。
18. 身為釣客，我希望賣魚、查行情、取消上架與修改草稿仍由規則引擎執行，以便平台動作維持可預測。
19. 身為釣客，我希望上架流程進行中不會同時出現 LLM 的側聊回覆，以便我不會混淆目前該填的欄位。
20. 身為使用者，我希望行情問題仍顯示既有的 7／30 個交易日行情卡，以便這次修正不犧牲原本的走勢功能。
21. 身為使用者，我希望模型不需要收到 30 天歷史、品質旗標與抓取時間，以便它只根據平均價與交易日期回答。
22. 身為維護者，我希望歷史訊息固定取最近 10 則，以便行為與 ADR-0011 一致。
23. 身為維護者，我希望每輪工具呼叫固定最多 2 次，以便沒有未文件化的隱藏上限。
24. 身為維護者，我希望 README 與 API 文件只列出真正支援的環境變數，以便部署時不會設定無效的開關。
25. 身為維護者，我希望領域文件列出 `sources` 卡片，以便文件與實際訊息型別一致。
26. 身為維護者，我希望 API 文件、流程文件與 UI 文件對來源卡的描述一致，以便 `CHAT`／`WEB` 的界線只有一種說法。
27. 身為維護者，我希望所有 AI 錯誤共用一個建構方式，以便新增錯誤碼時不用改五個地方。
28. 身為維護者，我希望 slots 只由後端驗證一次，前端直接信任後端結果，以便兩份驗證不會逐漸分叉。
29. 身為維護者，我希望 intent 使用共用常數而不是散落各處的字串，以便新增或改名時不會漏掉分支。
30. 身為維護者，我希望使用者文字與回覆來源使用不同名稱，以便閱讀程式時不會把兩者搞混。
31. 身為維護者，我希望工具迴圈從 AI service 拆出，以便每個檔案都在 200 行以內且職責清楚。
32. 身為維護者，我希望停用的網路工具被呼叫時回報為不合格輸出，而不是借用平台數字防護的錯誤碼，以便錯誤碼只有一種意義。
33. 身為維護者，我希望前端 AI 測試共用同一份 API stub 與使用者 fixture，以便新增測試時不用再複製貼上。
34. 身為維護者，我希望這次修正只使用既有的後端端點與前端流程接縫，以便不新增測試層。
35. 身為使用者，我希望交易房完全不呼叫 LLM 的行為維持不變，以便私人交易對話不會送到外部服務。
36. 身為使用者，我希望 Beta 的免費層限制、停用開關與靜默 fallback 行為維持不變，以便這次修正只修問題、不擴大承諾。

## Implementation Decisions

### 個資遮蔽

- 遮蔽仍由單一 redaction 模組負責，輸入是訊息文字與 context 中的字串欄位；鍵名與非字串值不處理。
- 地址樣式必須有行政區錨點才成立：至少包含「市／縣」或「區／鄉／鎮／市」其中一層，再接「路／街／大道／巷／弄」，可選擇性接門牌與「里／鄰」。單獨出現的「路」「弄」不得觸發遮蔽。
- 電話樣式新增 `+886` 國際碼、含括號的區碼（例如 `(02)12345678`）與常見分隔符；行動電話與市話都視為個資。
- Email 與身分證字號維持現行格式，但補上邊界測試，避免前後文被吃掉。
- 遮蔽後的查詢才可送給 Tavily；對話歷史與 context 摘要送給 Gemini 前也要先遮蔽。

### 歷史與重試錨定

- 歷史查詢改為接受一則錨定訊息：只取同一間助手房、序號小於或等於錨定訊息的使用者／助手訊息，再由近到遠取最多 10 則。
- 錨定訊息必須是最後一則 user turn；若歷史因限制或資料異常而缺少它，後端要把它補回最後一則，不能讓模型只看到更早的內容。
- 重試沿用原本的 `message_id`；後端以資料庫中的訊息為準，不信任前端文字，也不把錨定訊息之後的新訊息送進模型。
- 交易房仍然完全不走這條路徑。

### 回覆長度與查詢範圍

- `reply_text` 的最終長度包含查詢範圍後綴，上限仍是 500 字。
- 後綴只在加入後仍不超過上限時附加；若會超限就省略後綴，保留原始回覆，不得因此回報 `LLM_INVALID_OUTPUT`。
- 數字防護與 slots 驗證仍在最後文字上執行，不能因為省略後綴而放寬。

### 逾時

- 每次 AI 回覆只有一個請求期限：一般回覆 8 秒；一旦這一輪執行 `web_search`，期限延長為 15 秒。
- 期限同時套用在 provider 呼叫與每一個工具執行；工具開始前若剩餘時間已用盡，直接視為逾時，不再呼叫下游。
- 行情工具把剩餘時間傳給行情查詢與上游抓取；上游請求出現在期限內被中止。
- 行情上游逾時要回報為 `LLM_TIMEOUT`（靜默 fallback），不是一般的 `LLM_UPSTREAM_ERROR`。
- 逾時後不得繼續等待被放棄的背景工作；回覆要先回到使用者。

### 來源與 intent

- `WEB` 的定義是「這一輪成功使用了網路資料」，不是模型自稱的 intent。
- 只要 `web_search` 成功且取得至少一個合法來源，而模型的 intent 不是平台意圖，後端就把最終 intent 升級為 `WEB`，並附上最多 3 個 `{ title, url }`。
- `CHAT` 永遠不帶來源；平台意圖也永遠不帶來源。
- 升級必須在輸出驗證與數字防護之前決定，讓網路回答套用 `WEB` 的嚴格數字防護。
- 前端仍只從後端回傳的 `sources` 畫一張來源卡；不自行推測來源，也不接受模型提供的來源。
- 原始 spec 第 177 行「`CHAT` 有 sources 時再寫來源卡」由本決議取代：有網路資料就是 `WEB`，因此來源卡只屬於網路回答。GLOSSARY、API 文件與流程文件維持「只有網路回答顯示來源」的一致說法。

### 行情工具的模型視圖

- `get_market_price` 對模型只提供：是否查到、官方代碼、官方名稱、地區、交易日期、每公斤與每台斤平均價、養殖標記。
- 不把 30 天歷史、品質旗標、抓取時間、來源 URL 放進模型的工具結果，也不讓這些數字進入數字防護的證據池。
- 行情卡仍需要完整歷史；後端在同一次查詢中保留完整結果給前端組卡，該結果不進入模型的可見內容。
- 價格與日期仍只能來自官方行情服務；查無資料時模型只能說「暫無行情」，且不得出現數字。

### 前端 intent 路由

- 後端 intent 是主要依據。規則引擎優先的情境限於：平台動作 `SELL`、`MARKET`、`CANCEL`、`EDIT`，以及上架流程進行中。
- `BUY` 不再否決後端的 `PRODUCT_RECOMMEND`。移除前端自製的 `PRODUCT_HINT` 關鍵字判斷；只要後端回傳合法的 `PRODUCT_RECOMMEND` 與商品結果，就寫入文字並產生商品卡。
- `PRODUCT_RECOMMEND` 仍只使用工具結果中的商品；context 進入 shopping 模式並更新 `last_cards`。
- `CHAT`、`WEB`、`UNKNOWN` 的處理維持現行規則：`UNKNOWN` 先走規則，規則無法處理才使用模型的文字。
- 平台意圖不產生模型文字，避免同一輪出現兩套答案。
- 前端不再重複驗證 slots 的型別與數字來源；後端已驗證過的 slots 直接使用。規則引擎自己的 slot 抽取仍保留。

### 設定與文件

- 歷史訊息固定為 10 則；移除 `LLM_HISTORY_LIMIT`，不再提供隱藏上限。
- 每輪工具呼叫固定最多 2 次；移除 `LLM_MAX_TOOL_CALLS`，不再提供隱藏上限。
- `LLM_TIMEOUT_MS` 與 `LLM_SEARCH_TIMEOUT_MS` 仍可調整，文件要說明一般回覆與網路回合的關係。
- 領域文件的卡片種類補上 `sources`（最多 3 個 `{ title, url }`，只由後端的 `web_search` 結果產生）。
- API、流程與 UI 文件同步更新來源卡的 intent 條件、`CHAT` 與 `WEB` 的差別、重試錨定與逾時行為。
- 根目錄 README 與後端 README 的環境變數清單只保留真正支援的項目。
- ADR-0011 不改；本次修正讓程式回到 ADR 已記錄的 10 則與 2 次上限。

### 錯誤碼與程式結構

- 停用的網路工具被模型呼叫時，回報 `LLM_INVALID_OUTPUT`：模型使用了未提供的工具，屬於輸出不合格，不再借用 `LLM_GUARD_REJECTED`。
- 建立單一的 AI 錯誤建構器，統一設定 `code` 與 `retryable`；provider、輸出驗證、結果映射與工具錯誤都共用它。
- 把工具執行迴圈從 AI service 拆成獨立模組；service 只負責開關、設定、歷史、驗證、log 與錯誤映射。
- 使用者文字與回覆來源使用不同名稱；`source` 不再同時代表兩者。遞增等待計數的函式改為能說明意圖的名稱。
- 前後端 intent 清單使用各自匯出的常數；前端分支不再使用裸字串。由於後端是 CommonJS、前端是 ESM，不強制建立跨執行環境的共用檔，但同一個執行環境內只能有一份清單。
- 前端 AI 測試共用一份 API stub、訊息 factory 與使用者 fixture；既有 `deal-fixtures` 模式是參考對象。
- 所有新增或修改的程式碼檔案不超過 200 行；若現有檔案已接近上限，優先拆出職責而不是壓縮。

### 相容性

- `POST /api/ai/reply` 的請求與回應形狀不變；唯一可見的行為差異是 `CHAT` 使用網路時回傳 `intent: "WEB"` 與來源。
- 前端寫入訊息仍使用既有訊息端點；`sources` 仍是既有卡片型別。
- 行情卡、商品卡與協議流程不改資料模型。
- 靜默 fallback、配額提示、重試按鈕與交易房隔離維持現行行為。

## Testing Decisions

好的測試只驗證外部行為：給定使用者訊息、歷史、context 與注入的外部服務結果，斷言 API 回應、送給 provider 的輸入、前端寫入的訊息與卡片。測試不應斷言內部函式呼叫次數、模組結構或私有欄位；唯一例外是既有的 provider／Tavily／行情上游注入點，因為那是本專案既定的外部依賴替身。

只使用兩個既有接縫，不新增單元或 e2e 接縫：

- **後端接縫：`POST /api/ai/reply`**。透過真實 Express app、暫存 DB 與真實登入，注入假 provider、假 Tavily fetcher 與假行情上游。既有 `ai-reply`、`ai-reply-history`、`ai-reply-errors`、`ai-reply-guard`、`ai-tools-market`、`ai-tools-products`、`ai-tools-web` 測試是直接前例。
- **前端接縫：送出訊息與重試流程**。用假的 `HaisenAPI` 回應 `/api/chat/message` 與 `/api/ai/reply`，驅動 `flow.submitText`／重試，斷言寫入的訊息、卡片與 context。既有 `ai-reply-flow`、`ai-intents`、`ai-quota-retry`、`ai-tool-cards`、`ai-recommendation` 測試是直接前例。

後端要涵蓋的行為：

- 一般文字含「路」「弄」時原樣送給 provider；`+886` 手機、含括號區碼市話、含里鄰地址、Email 與身分證被替換成 `[已遮蔽]`。
- 建立訊息 A 後再建立訊息 B，對 A 呼叫回覆時，provider 收到的最後一則 user turn 是 A，且 B 不在歷史中；重試不新增使用者訊息。
- 495 字左右的 `PRODUCT_RECOMMEND` 加後綴後仍回 `handled: true`，最終文字不超過 500 字；後綴被省略而不是整則失敗。
- 行情上游延遲超過期限時，端點在期限內回 `handled: false`、`error_code: "LLM_TIMEOUT"`；含 `web_search` 的回合可使用較長期限。
- `web_search` 成功、模型回 `CHAT` 時，回應變成 `intent: "WEB"` 且 `sources` 最多 3 個；沒有網路結果的 `CHAT` 維持 `sources: []`。
- 行情工具送給 provider 的結果不含歷史、品質、抓取時間與來源 URL；同一回應中給前端的行情資料仍保留卡片所需的歷史。
- 模型要求第 3 次工具呼叫時回 `LLM_GUARD_REJECTED`；歷史輸入最多 10 則；移除環境變數後行為仍固定。
- 停用網路工具時模型要求 `web_search`，回 `LLM_INVALID_OUTPUT` 並 fallback。

前端要涵蓋的行為：

- 規則引擎判為 `BUY`、後端回 `PRODUCT_RECOMMEND` 時，畫面出現模型文字與工具產生的商品卡，不再被 `PRODUCT_HINT` 關鍵字擋下。
- `SELL`、`MARKET`、`CANCEL`、`EDIT` 與上架流程中仍由規則引擎優先，不寫入模型文字。
- `WEB` 回應的來源卡最多 3 個且只接受 http(s)；`CHAT` 不產生來源卡。
- 重試沿用原本的 `message_id`，不會重新送出使用者訊息；重試期間送出的新訊息不影響重試結果。
- 長回覆不被前端截斷或丟棄。
- 共用測試 fixture 後，既有 AI 測試的行為斷言不變。

文件沒有自動化測試接縫；以人工核對本次行為與 `docs/spec/`、`GLOSSARY.md`、兩份 README 是否一致，並在最終驗收列出核對結果。

## Out of Scope

- 新增 Playwright e2e 或 redaction 專用單元接縫；本次只沿用既有兩個接縫。
- 新增 allowlist、app 層使用額度、UI 隱私提示、串流、多模態、語音、模型選擇器、搜尋快取或自動重試。
- 升級到付費 AI Studio、Vertex AI 或 Google Search grounding。
- 重寫規則引擎的 intent 判斷、行情卡視覺設計或商品推薦排序。
- 修改交易房流程，或讓交易房使用 LLM。
- 改寫歷史功能 spec；本次以新 spec 記錄 `CHAT`／`WEB` 的解釋，舊 spec 保留為歷史文件。
- 全面重整所有前端測試 fixture；只整理本次 AI 相關、重複最明顯的測試樣板。
- 變更 Gemini 或 Tavily 的 provider 協定、模型名稱或錯誤碼詞彙表。

## Further Notes

- 這是 Beta 修正，不改變 soft launch 定位、免費層限制或 SLA 承諾。
- `WEB` 的定義是「用過網路資料」；這是本次解決原始 spec 內部矛盾的關鍵決議。之後若要做「一般知識也可引用網路但不顯示來源」，應另開 spec，不要回頭放寬 `CHAT`。
- 行情工具的「模型視圖」與「卡片視圖」是刻意的分離；任何新增欄位都要先問它是否應該被模型看見。
- 逾時是整個請求的期限，不是每個工具各自 8 秒再加總；新增工具時必須接受剩餘時間，不能自行建立更長的 timeout。
- 200 行限制是硬規則。AI service 拆分後，若任何檔案仍超過上限，應再依職責拆檔，而不是壓縮程式碼。
- 文件同步視為驗收條件：行為、API 形狀、環境變數或卡片型別一有變動，就要在同一個變更更新相關 `docs/spec/`、`docs/adr/`、`GLOSSARY.md` 與 README。
- 原始 review 的 Standards 異味清單是判斷題；本 spec 已把要處理的項目寫成決策，未列入 Out of Scope 部分者不強制一次修完，但不得讓新程式碼加深同一問題。
