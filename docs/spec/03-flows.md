# 03 使用流程

每條流程都標記狀態。**現況段落描述程式現在真的會做的事**；未實作段落是目標行為。

---

## F1 註冊與登入 ✅

**觸發**：使用者開啟任一頁面，或點導覽列的登入。

**流程**

1. 未登入時，助手面板只顯示登入引導，不建立房間。
2. 登入頁以手機號碼 + 密碼登入，或用手機、密碼、暱稱註冊。
3. 成功後存下 Token 與會員資料，導回原頁面。
4. 任一頁載入時，若有 Token 就向後端確認身分；失敗就登出並回到未登入狀態。
5. 登入後若沒有任何助手房，自動建立一間並載入歷史訊息；已有助手房則開啟最近一間。

**規則**

- 註冊不帶角色；使用者是單一帳號型態，買方／釣客由交易推導（ADR-0005），不影響任何操作。
- 未登入可以瀏覽商品，但**不能開助手房**（與舊計畫書的「未登入可導購」不同，以現況為準）。
- Token 只存在伺服器記憶體，後端重啟後所有人需重新登入。
- 登出會清除本機 Token、會員資料與助手記憶體狀態；重新載入任一頁都維持未登入。

**失敗**：電話重複註冊回 409；密碼錯誤回 401，畫面顯示錯誤訊息。

**目標變更（#30、#31、#32、#34，已完成）**

- 註冊表單新增縣市（必填）；API 驗證並把「臺」正規化為「台」。demo 種子資料已含固定且合法的縣市，啟動不再補值。
- 登入後若沒有任何助手房，建立一間；否則開啟最近一間。收件匣可新增多間助手房，每間有自己的 context 與草稿。
- 登入／註冊頁左側（釣客／買家文案下方）顯示法規告知與「漁業法」連結；兩個 tab 都顯示。
- 左側文案修正：「澎湖魚市」→「官方行情」、「下單」→「洽談後成立訂單」；並刪除「隔日清晨低溫直送」。

## F2 對話式上架 ✅

**現況**：處理方式自由文字、批次追問、整批售價必填／每台斤選填、行情卡與重量試算、修改草稿與取消上架、販賣法規確認、自由文字修改與取消後開新對話均已完成。上架不再詢問重量，也不再自動計算整批。

**觸發**：使用者說「我要賣魚」「剛釣到石斑」「出售」等。

**流程**

1. 若使用者尚未完成販賣確認（`seller_terms_accepted_at` 為空），先顯示法規告知卡；確認後清除先前對話紀錄，只留下「請問想要販售什麼魚類？」；取消則回 idle。確認一次永久跳過。
2. 意圖判斷為「賣」→ 助手房進入上架模式，建立空草稿。
3. 一次抽出句子裡所有能辨識的欄位。魚種未定時只問魚種；魚種確定後先一次列出尾數、處理方式與照片，之後缺什麼一次只問一個。
4. 追問順序：魚種 → 尾數 → 處理方式 → 照片 → 整批售價。
5. 照片只能由上傳事件填入，不從文字推測。
6. 非價格欄位齊了 → 查該魚種在釣客縣市的行情，送出一張行情卡：
   - 平均價（元／台斤）、當地縣市近 7 或 30 個交易日的走勢、期間最高／最低。
   - 縣市或全國平均、交易日期、來源。
   - 重量試算：使用者自行輸入重量並切換台斤／公斤，參考價格即時計算；空白或非正數顯示 `—`。
7. 若尚未提供售價，助手接著問：「請問整批要賣多少錢？（也可以一併說每台斤價格）」；若使用者已提供售價，直接顯示草稿卡／確認上架，不重問。
8. 售價規則：
   - 整批售價必填且必須大於 0。
   - 每台斤售價選填；只填每台斤、沒有整批價時回「請提供整批售價」，不建立商品。
   - 兩者都填 → 都保留，不檢查一致性；整批可視為折扣。
   - 不再自動計算整批，也不標「自動計算」。
9. 草稿卡顯示魚種、尾數、處理方式、照片、整批售價、每台斤售價（若有）；不顯示重量。
10. 「修改草稿」→ 助手問「你想修改哪一項？（魚種、尾數、處理方式、照片、售價）」→ 使用者用文字說欄位，或一句話同時說欄位與新值 → 更新該欄位；一次只改一個欄位，聽不出欄位時用文字重問；中途取消則回到修改前草稿。修改時說「取消上架／取消販售／不賣了」→ 直接進取消確認；只說「取消」→ 只取消本次修改。
11. 「取消上架」→ 助手問「確定取消上架？此對話會刪除，並開啟新的 AI 對話。」→ 確認後取消草稿、刪除目前這間 AI 對話，並建立、開啟一間新的助手房。
12. 「確認上架」→ 建立商品 → 回覆「已上架：{標題}」；發布後清空對話，只留下「已上架」那一則，草稿狀態歸零。

**欄位規則**

| 欄位 | 規則 |
| --- | --- |
| 魚種 | 先保留使用者原字串，再用名稱或別名查官方代碼；查不到 `species_code` 留空，多候選先回問 |
| 尾數 | `數字 + 尾/條/隻/份`；裸數字依下方判定順序處理 |
| 處理方式 | 自由文字，保留使用者原句；最多 20 字，且不能只有數字或單位；提示詞只舉例「活體、放血冰鎮」 |
| 照片 | 上傳後壓縮（長邊 1280、JPEG 0.75）再送後端 |
| 整批售價 | 必填；明確標記（`9000元`、`整批／總價／價格／售價 9000`）或價格步驟的裸數字 |
| 每台斤售價 | 選填；`每台斤 300`、`300元/台斤` 等明確標記 |
| 重量 | 不再詢問；使用者提到重量時先移除，不寫入草稿 |

**數字判定順序**

1. 先套明確單位與標記：尾數（`2尾`）、每台斤（`每台斤 300`）、整批價（`整批 9000`、`價格 9000`、`9000元`）。
2. 重量不再收集；`3公斤`、`2台斤` 只用來避免其中的數字被誤認為尾數。
3. 只剩尾數一個欄位缺 → 裸數字直接補該欄位；若該欄位正被詢問，四位數以上也接受。
4. 一次出現多個裸數字 → 一律回問，不自動補齊；四位數以上且無標記不自動補任何欄位。
5. 價格只在價格步驟、修改售價，或上述明確標記時寫入；裸數字永不寫入價格。
6. 無單位小數不視為尾數。

**規則**

- 上架地點預設帶入個人檔案的縣市與地址（後端會補）。
- 商品標題由後端產生：`{魚種}（{尾數}尾 / {處理}）`。
- 使用者說「算了」「不要了」→ 清空草稿、回到閒置。
- 同一句話可以一次補完多個欄位（例：「石斑 1 尾 放血冰鎮 2800元」）。
- 既有處理方式為「冷凍」的商品與其上架訊息，啟動時改成「放血冰鎮」並重算標題；已成交訂單中的商品快照不變。

## F3 導購與找魚 🟡

**觸發**：使用者說「今天有什麼魚」「有沒有石斑」「新北市有什麼」等。

**流程**

1. 意圖判斷為「買」→ 進入導購。
2. 從句子抽出：魚種名稱與縣市；不再解析料理方式或肉質。
3. 抓可售尾數 > 0 的商品（上限 100 筆），以 `fish_species` 與地區過濾。
4. 最多回 5 張商品卡，先說「找到 N 筆商品」。
5. 記住這批卡片的順序，供下一句指涉。
6. 使用者說「第 2 個」「這尾」「最後一個」時，對到卡片並接續該商品的諮詢；選取結果寫入 context。

**規則**

- 只推薦**還有可售尾數**的商品。
- 沒指定地區時，一律用個人檔案的縣市，並在回覆中說明「依你的地區」；句子明確提到其他縣市才改變範圍。
- 個人檔案沒有縣市時改為全省查詢，並在回覆中說明目前採用全省。
- 魚種以官方字典的官方名稱或別名比對；查無名稱時不強制過濾魚種。
- 查無結果時回「目前沒有符合條件的商品，可以換個魚種或地區」，並說明目前查的是哪個地區；不編造商品。

**已知缺口**

- 行情意圖已於 #25 實作；助手會依魚種與地區查詢行情，成功時回傳一張行情卡。

## F4 指涉與商品資訊 ✅

**觸發**：使用者在助手房說「第 2 個」「這尾」「最後一個」。

**流程**

1. 用 `last_cards` 與序數／指示詞對到上一批推薦卡。
2. 取得商品詳情。
3. 回覆魚種、尾數、處理方式、整批價、可售尾數與保存建議。
4. 選取結果寫入 `selected_product_id`，供下一句指涉。

**規則**

- 商品卡與推薦卡沒有「深入諮詢」按鈕；洽談一律走「洽談購買」。
- 回覆只能引用商品資料，不得自行評價「很新鮮」「超值」。
- 回覆不顯示重量（重量為 legacy 時也不顯示）。

## F5 洽談購買與交易房 ✅

**觸發**：使用者在商品卡或推薦卡按「洽談購買」。

**流程**

1. 檢查登入；未登入先導去登入頁。
2. 由商品的釣客找出（或建立）「買家 + 釣客」的交易房。
3. 房間進入真人模式，插入系統訊息「已進入交易洽談」。
4. 找出或建立該房的一筆訂單草稿，把商品與預設數量 1 加進去。
5. 面板切換為交易房視圖：對方名稱＋評價星星＋電話、浮動商品條、訊息流、輸入框。

**規則**

- 商品卡與推薦卡固定以數量 1 開啟交易；數量在發送交易面板調整。
- 電話在交易房標題列直接顯示完整號碼，附 `tel:` 連結，不做遮蔽。
- 同一釣客的多個商品進同一間房、同一筆訂單。
- 不同釣客 → 另一間房、另一筆訂單。
- 交易房裡的訊息**不會**觸發助手回覆。
- 已有一筆草稿時，再次洽談購買或加購都直接加入或累加進該草稿，不清空既有商品；加購面板可一次加入多項。
- 訂單已送出提案 → 商品條只顯示目前訂單，不再提供加購。
- 已成交 → 建立新的草稿訂單，同一間房。

**現況**：`POST /api/deals/initiate-channel` 建立或沿用交易房與 `DRAFT` 訂單；交易房的系統訊息計入未讀，對方輪詢時會看到紅點與新訊息。

## F6 訂單草稿與加購 ✅

**流程**

1. 交易房訊息區頂端固定顯示浮動商品條；每個商品一列，顯示魚種、處理方式（若有）、`剩 N 尾`、`N 元/台斤`（沒有時顯示整批價）。
2. 買家在草稿階段看到 `加購`、`發送交易`；釣客只看到唯讀商品條。
3. 按 `加購` 展開面板並取代商品條，列出同一位釣客的公開商品（`ACTIVE`／`PARTIALLY_RESERVED`，含已加入訂單的商品）。
4. 每列顯示魚種、處理方式（若有）、`剩 N 尾` 與每台斤或整批價格，並可填 `加購數量`；可再加購尾數 = 商品可售 − 該商品已在草稿中的尾數，0 時停用。加購列不顯示 legacy 重量。
5. 按 `確認` 收集所有大於 0 的列，呼叫 `POST /api/deals/items/batch` 一次加入，只留一則系統訊息。
6. 草稿不保留庫存；同一筆草稿的累計尾數不得超過目前可售，送出提案時再依當下可售檢查一次。

**規則**

- 商品條不提供逐項加減、刪除或清空；要調整組合時取消協議後重新發起。
- 草稿可以為空；沒有項目時 `發送交易` 停用。
- 小計 = Σ(每尾均價 × 尾數)；整單金額預設等於小計，可議價。
- `取消` 只收起加購面板，不改訂單；沒有可加購商品時顯示「目前沒有可加購的商品」。

**現況**：批次加購、浮動商品條與發送交易面板已完成；舊的訂單摘要 accordion、逐項加減、刪除、清空與「協商完畢」已移除。

## F7 協議確認、取消與重新發起 ✅

**觸發**：買家按商品條的 `發送交易`，填整單售價、面交地點、面交時間。

**流程**

1. 驗證：參與者、至少一個項目、逐項尾數 ≤ 可售、售價 > 0、面交地點與時間必填。
2. 草稿 → 等待確認，鎖定 30 分鐘。
3. 發起方自動視為已簽，交易房插入協議卡；發起人看到無按鈕版本。
4. 收件方按 `確認` → 成交：各項目計入已售、雙方完成數 +1、協議卡徽章變 `已確認`、插入評價卡。
5. 收件方按 `取消` → 在協議卡位置顯示確認取消卡；填寫自由文字原因後送出。
6. 送出取消 → 訂單轉 `CANCELLED`、立即釋放保留、協議卡同步 `已取消`、雙方看到「協議已被取消」卡與原因。
7. 取消後留在交易房；買家按 `發送交易` 可重新發起，複製最後一筆已取消訂單的項目與數量。

**規則**

- 只有收件方且狀態為等待確認時能按 `確認`／`取消`；發起人沒有按鈕。
- 已確認、已取消與已逾時的協議卡只顯示狀態，不再顯示任何操作。
- 只能改整單金額，不能逐項改價。
- 可售不足時回 409 並指出是哪個商品。
- 協議卡狀態要跟著訂單狀態更新（等待確認／已確認／已取消／已逾時）；舊資料的 `已退回` 仍可顯示。
- 取消原因為自由文字，最多 200 字；`cancel_reason` 固定寫 `OTHER`，原文存 `cancel_note`。
- 重新發起只適用買家與 `cancel_reason = OTHER`；每項數量上限為目前可售，可售 0 的項目略過，只留一則系統訊息。
- 對方不需重開房間：前端輪詢 `GET /api/conversations` 的 `last_order`，狀態或更新時間改變就重取訂單，協議卡與房間摘要會跟著更新。

**現況**：確認、取消（自由文字原因）、取消訊息卡、重新發起與輪詢同步均已完成。舊的 `退回` 與 `NEGOTIATING` 重送流程不再出現在新介面，僅保留舊資料相容。

## F8 逾時釋放 ✅

**觸發**：讀取商品清單、商品詳情、對話清單或訂單明細。

**流程**

1. 掃描所有進行中訂單。
2. 等待確認且鎖定過期 → 取消，原因「鎖定逾時」。
3. 舊 `NEGOTIATING` 且保留過期 → 取消，原因「協商逾時」。
4. 同步協議卡狀態、插入系統訊息、釋放尾數。
5. 商品狀態自動重算。

**現況**：`GET /api/products`、`GET /api/products/:id`、`GET /api/conversations` 與 `GET /api/deals/:id` 都會先掃描；重複掃描不會重複取消或重複留言。逾時取消不提供重新發起。

## F9 評價與交易紀錄 ✅

**流程**

1. 成交後，雙方在交易房看到評價卡。
2. 選 1–5 星（預設 5 星）、最多 3 個標籤、100 字內評語，按 `確認` 送出。
3. 四個標籤：`魚貨新鮮`、`準時守約`、`溝通良好`、`臨時放鳥`；已移除 `包裝完善`。
4. 每人每筆訂單限評一次；重複送出回 409。
5. 送出後重算對方平均星等與評價數；含「臨時放鳥」標籤時未到次數 +1，累計 3 次列入黑名單。
6. 送出後顯示「你已經送出評價。」；對方已評顯示「雙方都完成了。」，未評顯示「等待對方評價。」
7. 個人抽屜的「交易紀錄」列出所有訂單：多品項、成交金額、商品快照、評價狀態。

**現況**：評價卡、四個標籤、星等與未到次數重算均已完成；商品詳情頁已移除，評價只保留在交易紀錄與評價卡。一方送出評價後，另一方透過訂單輪詢在 3 秒內看到評價卡更新，不需重開房間。

## F10 行情查詢與上架引用 🟡

**現況**：按需抓取、21 市場對照、查詢 API、助手行情問答與上架行情卡已完成（#21～#29）。2026-10-28 起查詢 API 每次重抓，商品不再保存行情快照。

**目標流程**

1. 查詢時按需抓取單一魚種（新鮮代碼、最近交易日或指定日期），正規化後 upsert；沒有每日全量 job。指定日期當日無資料時往回抓 7 個日曆日補最近交易日，回應仍以實際 `trade_date` 與 `<= date` 的最近一筆為準。
2. 上架的非價格欄位齊了 → 查行情 → 行情卡（平均價、走勢、縣市／全國、日期、來源、重量試算）→ 問整批售價。
3. 商品發布不查行情、不寫入任何行情欄位。
4. 商品卡與推薦卡不顯示行情。
5. 使用者問「石斑現在多少錢」→ 助手查詢後回傳行情卡（平均價、縣市或全國、日期、來源、走勢）；數字只能來自查詢結果。
6. 查無資料或上游失敗 → 「暫無行情」。

**規則**

- 行情是批發平均價，不是售價；上架售價與成交價是另外兩個價格。
- 商品沒有行情快照；商品改價與行情更新互不影響。
- 抓取失敗不得覆蓋既有資料；有快取就回快取，沒有就回 `found:false`／`UPSTREAM_UNAVAILABLE`。
- 行情只抓新鮮資料：排除 `3xxx`／`6xxx`；`1xxx` 只允許海鱸、虱目魚、鰻魚；`4xxx`／`5xxx` 照抓，名稱有「養」者標養殖。
- 查詢 API 支援 `include=history&days=7|30`，供行情卡走勢；查詢 API 每次請求都重抓上游。

## F11 收件匣、未讀與輪詢 🟡

**流程**

1. 面板開啟時載入對話清單與當前房間訊息。
2. 每 3 秒輪詢增量訊息；分頁切到背景時暫停。
3. 收到新訊息 → 更新未讀數，顯示在右下角按鈕上。
4. 點收件匣 → 列出進行中與歷史房間，顯示對方、最後訊息、未讀、訂單摘要。
5. 進入房間即標記已讀。
6. 面板關閉再開會重新載入；**不會**記住上次的房間與捲動位置（目標要記）。

**未讀規則**：助手房的系統訊息不算未讀；交易房的系統訊息（開房、加購）算未讀，讓對方知道有新的洽談。

**現況**：助手房與交易房都會出現在收件匣；#30 已完成多間助手房的新增與切換，#31 已完成刪除與最後一間的空狀態；交易房的訂單摘要來自進行中的 `deals`。2026-10-27 起，對話摘要另回 `last_order`（不限狀態的最新訂單）與 `orders`（房間所有訂單摘要），輪詢據此在協議成交、取消、逾時或評價後更新協議卡、評價卡與房間摘要，讓非操作方不必重開房間就看到更新。
