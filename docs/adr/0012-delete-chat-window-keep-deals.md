# 0012 刪除對話：未成交資料清除，已成交訂單保留

## 背景

原本 `DELETE /api/conversations/:id` 只允許助手房、純聊天房，以及全部訂單皆 `CANCELLED` 且沒有成交歷史的交易房。進行中訂單與已成交房間都不能刪。

實際需求是「刪除對話」，不是刪除交易。使用者要清掉收件匣裡的對話，但已成交的訂單、金額、評價與交易紀錄必須繼續存在。另一方面，協議還沒成立的訂單沒有保留價值，刪房間時可以一起清除。

## 決策

- **任何房間、任何時候都能刪。** 不再檢查訂單狀態，`deletable` 恆為 `true`。
- **房間與訊息一律硬刪。** 移除 `conversations` 資料列與該房所有 `messages`；不使用 `archived` 或 soft delete。
- **沒有 `CONFIRMED` 訂單時，一併刪除所有 `deals` 與訂單項目。** 包含 `DRAFT`、`PENDING_REVIEW`、`NEGOTIATING` 與 `CANCELLED`；保留尾數因訂單消失而釋放。
- **有 `CONFIRMED` 訂單時，只保留已成交訂單。** `CONFIRMED` 的 `deals`、項目快照、`review_status` 與 `reviews` 保留；其他未成交訂單與項目刪除。
- **已成交訂單的 `conversation_id` 只作歷史參考。** 房間已不存在；交易紀錄與單筆訂單查詢不得再依賴那個房間。
- **房間 ID 不重用。** 每日流水號存於 `counters`（與商品相同），硬刪後仍保留計數，避免舊訂單的 `conversation_id` 誤指到新房間。
- **刪除後再交易會開新房間。** 交易房唯一鍵 `buyer_id + seller_id` 只計算現存房間；舊房不會被重新啟用，舊成交紀錄留在交易紀錄。
- **成交事實保留。** 商品的 `sold_quantity` 與雙方的 `completed_deals` 不回滾，因為漁獲實際已售出。

## 取捨

- **好處**：收件匣可以真的清乾淨；交易紀錄、評價與成交數不受影響；未成交的洽談資料不會殘留；房間 ID 不重用，不會把舊訂單接到新對話。
- **代價**：已成交訂單失去對話，`conversation_id` 變成歷史值；若交易房刪除時還有人沒送出評價，就沒有對話內的評價卡可以補評；交易紀錄的「成交筆數」可能多於看得到的房間數。
- **刻意不做**：`archived` 房間保留與重新啟用；soft delete；連已成交訂單或評價一起刪；回滾商品已售量或成交筆數；為已刪房間提供唯讀對話。

## 替代方案

- **沿用 archived 房間。** 保留房間列隱藏，之後再交易時重新啟用。可保留 `conversation_id` 完整性，但違反「不再重用的房間直接刪除」，也讓舊訊息與新交易混在一起。
- **只允許取消後刪除。** 就是原本規則；進行中與已成交房間無法清理，與需求衝突。
- **連已成交訂單一起刪。** 最徹底，但買家的交易紀錄與評價消失，也無法避免用刪房間洗評價。
- **改成 per-user 隱藏。** 只從自己的收件匣移除，對方仍保有對話。需求是雙方都移除對話，且會讓同一房間出現兩套可見性規則。

**Status**: accepted（2026-11-15）

**Considered Options**:

- 保留 archived 房間並重用。
- 只允許取消後刪除。
- 連已成交訂單一起刪。
- 每位使用者各自隱藏。

**Consequences**:

- `GET /api/conversations` 不再需要檢查可刪性；`deletable` 恆為 true。
- `DELETE /api/conversations/:id` 回 `{ deleted: true, kept_orders: N }`。
- 交易房刪除後，未成交訂單不再出現在交易紀錄；已成交訂單與評價仍在。
- `conversations` 的每日流水號由 `counters` 保護，硬刪後不重用。
- ADR 0001 的「一組人一間房」修正為「同時最多一間未刪除的房間」。
