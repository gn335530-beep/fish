# 0009 商品可下架、可重新上架，刪除為不可逆硬刪

## 背景

原本商品一旦上架就沒有下架或刪除機制：`docs/spec/02-domain.md` 明文寫「商品沒有下架狀態；本版不提供刪除」。這讓釣客無法停止販售剩餘尾數，也無法清掉已售完或不想再賣的商品。公開列表因此會一直保留 `SOLD_OUT` 商品，買家看到的不是「現在買得到」的清單。

## 決策

- **下架可逆**：新增 `delisted_at`。商品下架後狀態為 `DELISTED`、可售視為 0，從公開列表移除，但保留在「上架紀錄」。
- **重新上架**：清空 `delisted_at`、更新 `listed_at = now`，狀態依「保留／可售」公式重算。只有還有未售尾數（總尾數 − 已售 > 0）的已下架商品可以重新上架。
- **刪除不可逆**：硬刪 `products` 資料列，不新增 `deleted_at`。`SOLD_OUT` 可直接刪除；`DELISTED` 可刪除；`ACTIVE`／`PARTIALLY_RESERVED` 必須先下架。
- **商品 ID 不重用**：每日商品流水號另存 `counters`，`nextProductCode()` 取 `max(當日現有最大流水號, counter) + 1` 並寫回。硬刪後 counter 仍保留。
- **既有訂單使用快照**：`CONFIRMED`／`CANCELLED` 訂單保留商品名稱、照片、金額與尾數快照；刪除商品不影響歷史訂單與評價。
- **照片保留**：刪除商品不刪 `backend/uploads/` 或 `backend/seed-assets/` 的照片檔，舊訂單快照與舊對話卡片仍可能顯示。
- **進行中訂單的處理**：下架或刪除時，`DRAFT` 移除該商品並重算金額；`NEGOTIATING` 自動取消（`cancel_reason = OTHER`、`cancel_note` 為「商品已下架／已刪除」）；`PENDING_REVIEW` 照走，買家仍可確認成交。
- **退回邊界**：商品已下架或已刪除時，買家在 `PENDING_REVIEW` 按退回（legacy API）會直接取消，不進入 `NEGOTIATING`。
- **公開列表**：`GET /api/products` 只回 `ACTIVE` 與 `PARTIALLY_RESERVED`；`GET /api/products/mine` 回登入釣客所有未刪除商品。
- **狀態仍由公式推導**：`DELISTED` 優先於保留與售完；狀態與可售尾數不落庫（延伸 ADR 0002）。

## 取捨

- **好處**：釣客能停止販售與清理商品；公開列表只呈現真的買得到的商品；歷史交易與照片不會因刪除而斷裂；ID 不重用避免舊連結或快取誤指到新商品。
- **代價**：商品有四個狀態與兩個時間欄位；刪除流程必須處理草稿、洽談中與等待確認三種訂單；`counters` 多一個要維護的集合。
- **刻意不做**：soft delete（`deleted_at`）與資料列保留；重用商品 ID；刪除照片檔；連帶刪除訂單或評價；要求有進行中訂單時不能下架。

## 替代方案

- **只做 soft delete**：保留資料列與 `deleted_at`，查詢時全部過濾。缺點是每條商品查詢都要記得過濾，漏一處就會露出來；也無法真正清除釣客不想留的資料。選硬刪＋照片／訂單快照保留。
- **刪除時一併刪除訂單與評價**：會讓買家的交易紀錄與評價消失，破壞歷史紀錄。選保留快照。
- **商品 ID 直接重用**：硬刪後最大流水號可能回落，新商品會拿到舊 ID，舊連結、快取或對話卡片可能指到錯的商品。選隱藏 counter。
- **有進行中訂單時禁止下架**：釣客可能因缺貨或不想再賣而需要停止販售；強迫先處理訂單會讓流程卡住。選允許下架，但取消 `NEGOTIATING`、保留 `PENDING_REVIEW`。
