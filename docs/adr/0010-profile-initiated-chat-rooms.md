# 0010 個人資訊可開啟交易房；無商品時純聊天

## 背景

原本交易房只能由商品開啟：`POST /api/deals/initiate-channel` 需要 `product_id`，房間固定是「買家 + 釣客」，並在開房時建立一筆帶商品的訂單草稿。商品卡上的「賣家資訊」按鈕只有入口，沒有行為；使用者無法先認識對方、再決定買什麼。

新的個人資訊頁要提供「聊聊」：買家可以從對方的個人資訊開交易房，先問問題或逛商品。對方可能完全沒有上架商品，這時房間不應該出現無法使用的購物車。

同時，交易房目前用 `buyer_id + seller_id` 當唯一鍵，方向固定；同一組人反向買賣時本來就會是另一間房。這次要把它明文化。

## 決策

- **沿用交易房，不新增「直接對話」房型。** 個人資訊的「聊聊」建立／沿用既有 `deal` 房；目前使用者是買家，被看的人是釣客。
- **有商品才建立訂單草稿。** 對方有公開商品時，找或建立空草稿，購物車顯示「尚未加入商品」與「選購」；對方沒有公開商品時，不建立 `deals` 資料列，`deal: null`，房間只聊天。
- **無商品時不顯示浮動購物車。** 只顯示訊息流與輸入框；房間仍可送訊息、計入未讀。
- **純聊天房可隨時刪除。** 沒有任何 `deals` 的房間不受「交易房需全部取消且無成交」限制；有訂單時沿用現行刪除規則。
- **房間方向固定。** 按「聊聊」的人是買家，被看的人是釣客；同一組買家與釣客只有一間，反向交易是另一間房。`GLOSSARY.md` 的「同一組人只有一間」改成方向性描述。
- **交易房標題列角色評分。** 有訂單時，買家看到對方的釣客評價（買家給的評價），釣客看到對方的買家評價（釣客給的評價）；純聊天房顯示整體評價。
- **電話維持顯示。** 交易房標題列直接顯示對方電話；純聊天房也一樣。按「聊聊」就能看到電話是刻意接受的隱私取捨。

## 取捨

- **好處**：個人資訊頁可以直接開始對話；不需要先選商品；有商品時才出現購物車，畫面不會出現無法使用的功能；沿用既有房間、訊息、訂單與權限模型，改動比新增房型小。
- **代價**：收件匣會出現沒有訂單的純聊天房；任何人按「聊聊」就能看到對方電話；房間角色仍是「買家 + 釣客」，即使對方目前沒有商品；同一組人反向交易會有兩間房。
- **刻意不做**：新的直接對話房型、無角色房間、同一組人雙向共用一間房、第一次回覆前隱藏電話、封鎖功能。

## 替代方案

- **新增直接對話房型**：沒有買賣角色、沒有購物車，要交易時另開交易房。語意最乾淨，但要多一組房間型別、收件匣、未讀、刪除與權限規則。
- **強制先選商品才能聊聊**：不改既有模型，但對方沒有商品時無法對話，與需求衝突。
- **無商品也建立空草稿並顯示空購物車**：實作最簡單，但畫面會出現「選購」卻沒有商品可選的空功能。
- **同一組人雙向共用一間房**：最符合「一組人一間」的直覺，但要改 `conversations` 的唯一鍵、訂單角色、協議與評價方向，範圍過大。

**Status**: accepted（2026-11-10）

**Considered Options**:

- 直接對話房型。
- 強制先選商品。
- 無商品仍顯示空購物車。
- 同一組人雙向共用一間房。

**Consequences**:

- `conversations` 維持 `assistant`／`deal` 兩種；純聊天房是沒有 `deals` 的 `deal` 房。
- `GET /api/conversations` 的 `deletable` 對純聊天房為 true；收件匣不顯示訂單摘要。
- 交易房標題列的評價來源依目前使用者的交易角色決定；純聊天房用整體評價。
- 電話在純聊天房仍可見；若未來要降低騷擾，需另做「第一次回覆後才顯示電話」或封鎖功能。
